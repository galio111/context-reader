# Context Reader Agent Guide

## Project

Context Reader is a Next.js 15 / React 19 app for Chinese-speaking learners reading real English articles. Reading flow is primary; lookup, translation, vocabulary, and Anki are supporting tools. The fixed production URL is `https://context-reader-ten.vercel.app`.

The current public-beta account entry is an unverified mainland-China phone identifier plus nickname registration and a six-digit numeric password. It uses server-side Supabase Auth with HttpOnly cookies, sends no SMS, and stores the password through Supabase's password hashing; the internal synthetic email must never be shown to users. Email OTP remains in the code only for legacy/future use and is not launch-ready until custom SMTP and a `{{ .Token }}` template are configured. Guests receive 10 word/phrase lookups per Shanghai day; cached guest lookups count, while registered cache hits and failed/cancelled work do not. Save/vocabulary/Anki/private translation/summary/OCR require login; admin-prepublished translations stay public. Structured and streaming lookup requests share one idempotent usage action while recording both upstream executions. Cloud sync is authoritative but must preserve local data through object versions, article deduplication/tombstones, and an isolated recovery store only for genuinely ambiguous vocabulary conflicts. Public recommendations, users, password resets, understandable ordinary-user quota rules, and private feedback share the unified `/admin` console; payment is not connected. Only a server-verified `admin` entitlement may expose the homepage Admin link or authorize `/api/admin/*`; the legacy password session remains a recovery entry and never replaces the developer-account check. The quota UI must hide raw metric keys, fixed window internals, developer safety allowances, and inactive price experiments. Whenever future work re-enables email login, proactively remind the user about the unfinished SMTP blocker.

## Commands

```powershell
npm install
npm run dev
npm.cmd run build
npm.cmd exec -- vercel --prod --yes
```

Pure documentation changes do not require a build or deployment. For user-facing code releases, run the production build and confirm Vercel reports the fixed production alias.

## Hard Boundaries

- Keep article text visually primary inside the reader. The homepage may use expressive spatial continuity and motion to teach real reading interactions, but it must keep article entry immediately available and must not become a generic AI landing page, game, or social feed.
- Article editing stays directly in the reading canvas. Read and edit modes must share typography and layout; do not replace the article with a textarea or controlled per-keystroke editor.
- Preserve explicit blank paragraphs. Imported images are read-only blocks but may be deleted as whole blocks while editing.
- Undo/redo is reading-session history, survives saves until returning home, and is not browser `execCommand` history.
- Mobile vertical movement is reading scroll. Phrase selection requires deliberate horizontal movement or long press.
- Full-article translation starts only from its sidebar. Opening the sidebar must not auto-start it, and switching tools must not cancel an active translation job.
- Translation runs one text block per request with full-article `contextBlocks`; unchanged blocks reuse cache, selective refresh touches changed blocks, and force-regenerate bypasses whole-article and per-block caches.
- Streamed word-explanation fields are the visible authority. Merge them into the structured result, cache the merged result, and keep fresh, completed, and replayed layouts identical.
- Regenerating a saved vocabulary item updates generated fields but preserves its id, creation time, and Anki import record.
- Vocabulary cards use measured content heights; do not restore fixed oversized rows or manual expand controls.
- Anki cloze hints use only the durable `contextMeaning`. Pronunciation is click-to-play; note import must continue if deck autoplay configuration cannot be written.
- Public recommendations are server-rendered. Any article, explanation-cache, translation-cache, import, or schema change must also be checked against `/admin` publishing, Supabase preload storage, and public-article cache replay.
- New public recommendations enter through one `/admin` candidate workflow. Browser-local saved articles, manual paste, and URL import are equal source modes; URL intake preserves meaningful article images and returns cover candidates. Manual URL intake and the recommendation crawler both reuse `/api/import-url`; keep article-boundary and noise filtering in that shared importer so navigation, source/citation panels, related/recommended stories, newsletters, comments, social tools, and other trailing site chrome never become candidate body blocks. `lib/articleContentSanitizer.ts` reapplies the safe trailing-boundary rule when old remote-URL candidates are read and before they are published, so previously stored crawler noise is not exposed or promoted; never apply that compatibility cleanup to plain pasted text. The system owns difficulty, audience, topics, reading time, and timeliness classification; the admin reviews the article, summary, and cover instead of manually classifying it. The editor only saves candidates, and publication exists only in the candidate list. Candidate and published-article rows open the real `ReaderView`, including lookup, vocabulary saving, translation, local saving, and in-place editing; ReaderView body edits must write back to the matching candidate or public row before leaving edit mode, while title/summary/cover metadata remain in the Admin editor. Candidate rows reuse `public_articles` with `published=false`, while classification, cover metadata, and source kind live in `imported_article.recommendation`. A recommendation cover is mandatory for publishing; inline article images remain optional. The recommendation crawler discovers from the code-reviewed RSS/Atom whitelist, deduplicates against public and candidate rows, imports and classifies at most two additions per run, and never publishes automatically. `/api/admin/article-crawler` provides manual topic/difficulty/target-inventory runs; `/api/cron/recommendations` rotates one topic daily and must fail closed unless `CRON_SECRET` matches.
- Feedback submitted through `/api/feedback` is private JSON in the `context-reader-feedback` Storage bucket and may reference up to three private JPEG/PNG/WebP/GIF attachments of at most 5 MB each. `/api/admin/feedback` is the only listing, attachment-view, status-update, and deletion path; deleting feedback also deletes its validated attachments. The Admin feedback UI shows product content, optional contact, source page, category, time, and image previews, but hides user-agent and storage implementation details. Treat missing status on older feedback as `new`.
- User-visible request failures must distinguish unsupported input, missing connectivity, account/quota boundaries, and site/provider faults; never expose raw browser messages such as `Failed to fetch`. Standalone dictionary input rejects Chinese-to-English requests and whole sentences immediately with an explicit current-capability explanation. Site, API, provider, configuration, and client-processing faults use a shared error id, persist detailed diagnostics under the private feedback Storage bucket, and appear only in the server-authorized `/admin?section=errors` view. Network/input errors are not developer bugs and must not be stored. Error email alerts are optional until `ERROR_ALERT_SMTP_*` or Resend is configured, must be deduplicated, and must never delay or replace durable Admin storage.
- Keep the API security boundary intact: bounded request bodies, cost-aware throttling and concurrency caps, same-origin admin mutations, pinned-DNS safe remote fetches, private-network blocking, and generic client errors. The in-process limiter is defense in depth; production abuse resistance also requires a platform/distributed rate limit or a provider spending cap when traffic grows.
- Supabase browser roles must never bypass server-side admin or public-content paths. Keep RLS enabled and revoke the three public-content tables plus server-only account tables/functions from `anon`, `authenticated`, and `PUBLIC` as defined by the authoritative SQL. The account SQL intentionally grants `authenticated` only the documented own-row permissions; the app browser still receives no Supabase key.

## OCR Boundary

- Legacy/shared `ArticleInput` code can still call `/api/ocr-image` and `/api/ocr-image-layout`, preserve the uploaded image, and use layout word boxes when available, but the shipped `/home-v2` homepage deliberately exposes no image-upload entry.
- Automatic OCR for images inside URL-imported articles remains disabled in `components/ReaderView.tsx`. Do not describe OCR as either universally enabled or universally disabled.
- `/api/ocr-image-url` and the provider layer are available, but reader-side automatic invocation is gated off.
- The image viewer supports cursor-anchored wheel zoom, layout-word clicks when stored, and remote image download through `/api/download-image`.

## Homepage Boundary

- `components/ArticleInput.tsx` and `components/ImmersiveHome.tsx` retain legacy/shared behavior only. `components/BookHome.tsx` and `docs/home-v2-implementation-contract.md` are the shipped homepage implementation and design contract.
- `/home-v2` is the primary and shipped homepage and the source of truth for future homepage work; `/` redirects to `/home-v2`. All home, return-home, logout-return, PWA start, and offline-home navigation must resolve to `/home-v2`.
- Suppress only the browser's native blue selection paint through the shared `::selection` rule, while restoring visible native selection inside inputs, textareas, editable fields, and the full-article translation panel. Never apply site-wide `user-select: none`: ordinary pointer movement, clicking, scrolling, dragging, input editing, and Context Reader's application-controlled word/phrase lookup must all remain functional.
- `/home-v2` is the approved primary book-space homepage. Its authoritative state order and motion boundaries live in `docs/home-v2-implementation-contract.md`. `app/home-v2/page.tsx` server-loads public articles and passes them to `HomeClient`; `HomeClient` selects `BookHome` only for the book variant and continues to own every real `ReaderView` transition. The fixed scene order is closed cover, developer foreword, start-reading spread, and recommendation spread. The complete scroll track and scrollbar exist from the closed-cover first frame. Scroll position, not timers or threshold-triggered autoplay, seeks every cover and inner-page frame: reversing the wheel at any point must reproduce the exact prior pose without flashes or input blocking. Directory jumps use one direct source-to-target sheet even when an intermediate chapter is skipped; they must not queue one turn per skipped chapter. The foreword keeps its left page blank and renders replaceable developer copy plus signature on the right. The start-reading spread keeps the real micro context demo on the left and defaults to standalone lookup on the right; paste and URL import remain same-page tabs and must not become separate chapters. The former full preference chapter is removed: the recommendation page keeps the central spine, shows a small daily-update marker, and opens the stage/pace/interest questions in a scrollable personalization dialog. Without a saved profile, default recommendations are daily-stable selections from CET-4, CET-6, postgraduate, IELTS, and TOEFL inventory, falling back to all covered public articles only when needed. A future reading-history profile should infer an initial level while always allowing manual correction. Image upload remains absent. Do not render a full-width top bar or any `CR` square mark; keep only the floating `Context Reader`, start-reading, and Menu controls. The selected book engine is the B hybrid route from `docs/book-model-direction-questionnaire.html`: a custom persistent 3D cover/spine/page-block shell plus the MIT `page-flip` engine for one soft DOM snapshot sheet, with Wawa R3F used only as a motion reference. Never restore the rejected vertical-strip turn. Desktop widths from 761–1280 px keep at least a 1160 px spread and crop both sides symmetrically instead of compressing the book. The original desktop cursor-letter trail is a confirmed brand effect: keep it clearly visible above the closed/open book, buttons, forms, and overlays; mask it only around the reading article and explanation-reading areas, and unmount it inside `ReaderView`. Mobile uses touch ripple only.
- Scroll remains the only source of page pose, but an in-progress cover or inner sheet must not stay suspended after input stops: after about 90 ms idle, settle that current sheet to the adjacent boundary in the last travel direction, with at most about 480 ms remaining motion so the soft-sheet curvature, reverse side, occlusion, and moving contact shadow stay readable. Any new wheel, touch, or scroll-key intent cancels the settle immediately and retakes control from the current frame. Click-driven cover and directory turns use the same cancellable request-animation-frame scroll controller with a capped duration rather than browser-native smooth scrolling.
- Treat the Home V2 paper turn as a protected motion system, not replaceable decoration. Preserve `soft` snapshot density, sine page lift, visible renderer overflow, a measurable `display:block` page-flip engine even while visually hidden, separate render/scroll endpoint epsilons, and the target-first/next-frame-clear handoff. New input must cancel pending cleanup. Any change to `BookHome`, `CurvedPageTurn`, their CSS, or book sizing must pass forward, reverse, mid-turn interruption, and direct directory-jump checks without upper-left displacement or a flash back to the outgoing spread. Exact invariants and values live in `docs/home-v2-implementation-contract.md`.
- On `/home-v2`, keep the floating start-reading action available outside the closed cover and keep standalone lookup, paste, and URL as equal modes inside the start-reading workbench. `HomeOptionMenu` opens as a right-side Staggered Menu with sequential underlay, panel, and item entrances; the closed Menu trigger stays unchanged. Its only entries, in order, are `使用说明`, `生词本`, `保存文章`, `账号与用量`, `意见反馈`, and developer-only `admin后台`. Every non-Admin item opens an in-place left preview on hover or keyboard focus and may be pinned by touch/click without navigating away; `admin后台` is the only Menu item that navigates to another page. A preview remains open while the pointer moves into and interacts with it, and changes only when another Menu target is selected or the Menu closes. On desktop, vocabulary, saved-article, and feedback preview top edges align with their matching Menu rows, including populated and empty states; the complete guide and account/usage page previews instead extend nearly full-height from the viewport top to bottom. The preview layer keeps the underlying homepage visible with a light blur, has no enclosing heavy card border, and gives long content its own local scroll surface. `使用说明` and `账号与用量` reuse their complete page bodies inside the left preview instead of reduced summaries, preserving their navigation, actions, detailed sections, and independent scrolling; guide reading actions jump directly to the paste workbench. `意见反馈` uses a wider preview, submits directly to the private feedback API, and accepts up to three optional images. The Menu footer always shows the nickname or `未登录`. `生词本` must not reopen the legacy click dialog: its left preview renders every matching entry through the existing virtualized, measured list pattern, keeps prefix search, and reveals a second full-detail pane with pronunciation and available source-sentence navigation when an entry is hovered or focused. Keep the legacy `VocabularyPanel` implementation intact for rollback. The saved-article preview remains vertically scrollable. The Menu never contains logout; logout belongs to `/account/usage`. Saved articles stay ordered by latest open time. A logical article must appear only once: merge identical bodies and legacy `-local-recovered-*` lineages into the original article, preserve the newest open time, never expose recovery copies in the saved list, and have the sync API tombstone recovery ids sent by stale browser tabs.
- Public recommendations must remain server-rendered through `app/home-v2/page.tsx`. Desktop book-turn behavior must not replace normal mobile vertical scrolling.

## Data And Compatibility

- Browser `localStorage` contains durable user data: saved articles, vocabulary, explanations, translations, and reading continuity. Failures should degrade gracefully and must not clear unrelated data.
- A failed live session check must enter an explicit limited offline mode instead of presenting a previously verified account as logged out. The minimal local identity snapshot may expose only that account's browser-local articles, vocabulary, reading state, and existing caches; it must never restore Admin, plan, quota, or API authorization. Offline local edits may queue for the existing sync path after live authentication returns. New AI work, URL import, OCR, feedback submission, cloud sync, and usage reads remain network-only and must explain that boundary in the UI.
- `SavedArticle.importedArticle` is optional for backward compatibility. When present, preserve rich blocks, inline `sup`/`sub`, images, OCR/layout metadata, and reading style.
- Explanation cache key: normalized selected word or phrase + source sentence. Article translations have whole-article and per-block caches.
- DeepSeek routes default to `deepseek-v4-pro` with thinking disabled. `DEEPSEEK_MODEL` is the shared override, `DEEPSEEK_TRANSLATION_MODEL` can override article translation alone, and the `DEEPSEEK_FALLBACK_*` variables configure model/provider fallback where supported.
