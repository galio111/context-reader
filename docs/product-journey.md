# Context Reader 产品历程

这份文档记录 Context Reader 从第一个可运行版本到最终完成之间的产品旅程：UI 如何变化、功能如何长出来、哪些方向被放弃、为什么改变，以及每个阶段真正学到了什么。

它不是当前需求书，也不约束未来必须保留某个旧设计。当前事实以代码、`AGENTS.md`、`PRODUCT.md`、`docs/architecture.md` 和专题契约为准；这里保留的是时间、选择和人的感受。

## 记录规则

- 每个已经完成的 UI、功能、基础设施里程碑都追加一条；重要的“接受但待实现”或“明确放弃”决策也记录。
- 明确标注状态：`已上线`、`已实现未上线`、`已接受待实现`、`已放弃`、`历史实现`。
- 每条尽量写清：之前是什么、变成什么、为什么、如何验证、证据在哪里。
- 记录用户明确表达的感受，但不替用户发明动机或情绪。
- Git commit 是技术流水证据；本文件聚合有意义的阶段，不重复每个备份提交和小修复。
- 新条目按时间追加在文档末尾。若旧记录有误，用勘误说明修正，不悄悄改写历史。
- 本文件保留曾经成立但后来被覆盖的决定。当前首页实现不得从时间线关键词搜索直接恢复旧结论，必须先读取 `docs/home-redesign-current-decisions.md`；结构化访谈原始选择见 `docs/home-redesign-interview-archive.md`。

## 2026-05-28：第一个可以阅读的版本

**状态：已上线历史版本**  
**证据：** `8836c4e`（Initial context reader app）

Context Reader 从一个非常直接的需求出发：把英文文章放进一个能安静阅读的界面，点击陌生词时获得中文语境解释。第一天很快补上音标、保存文章、文章摘要、DeepSeek 结果兜底和清空/返回后的输入状态。

这一阶段确立的主线后来一直没有变：真正重要的不是“AI 聊天”，而是让解释留在阅读上下文里，让用户少离开文章。

## 2026-05-28—05-30：从能用到能持续阅读

**状态：已上线**  
**证据：** `8f7b815`—`1f0141f`

保存文章库、摘要生成与重新生成、移动端工具控制、解释面板滚动和桌面侧栏定位陆续补齐。文章不再是一次性的输入；它开始具有“回来继续读”的连续性。

这个阶段也形成了一个长期经验：移动端的空间与手势不能照搬桌面。解释面板是否能正常滚、工具是否遮住正文，看起来是局部 UI 问题，实际上决定了阅读是否仍然是主体验。

## 2026-05-29—06-11：学习闭环出现

**状态：已上线并持续演进**  
**证据：** `6a8b01c`、`5aac510`、`a65b338`、`aa05cbc`、`85ee81e`、`b0be156`

句子追问、浏览器侧 AnkiConnect、自动补齐 Anki 模型字段、生词本发音和 Anki 发音按钮让“读懂一个词”第一次接上了“以后还能复习这个词”。

后来这条链路继续升级为统一云端美音/英音、完整 note 模板、持久 `contextMeaning` 提示和失败时不创建残缺卡片。功能越来越复杂，但核心仍是学习资料必须耐用，不能只在生成当下看起来丰富。

## 2026-07-14—07-15：从单机工具变成有账号的产品

**状态：已上线**  
**证据：** `42c1258`—`f257ead`

项目加入账号、额度、用量记录和跨设备学习数据同步。最初探索过托管邮箱登录，随后切换到更适合公开测试的“大陆手机号标识 + 昵称 + 6 位数字密码”，不发短信，也不把内部 synthetic email 暴露给用户。

同步经历了原子计数、空响应、冲突目标和退出前数据安全等修正，最终发展为 bounded snapshot、opaque cursor、CAS 版本、tombstone 和本地恢复边界。这个阶段把“本地数据不能丢”从偏好变成了系统级规则。

## 2026-07-15—07-16：推荐内容和 Admin 成为真实系统

**状态：已上线并持续演进**  
**证据：** `a3bdb47`、`ede30f3`、`ebdcbe7`、`278589d`

推荐文章从静态展示发展为候选工作流：保存文章、粘贴和 URL 可以进入候选，系统做分类，管理员审核封面和摘要，发布后在真实 `ReaderView` 中阅读。随后加入代码白名单 RSS/Atom 抓取器、统一 Admin、开发者账号权限和反馈收件箱。

后来又补上正文边界清理、第一方 WebP 封面、手动/定时补充、错误后台和真实 Reader 编辑回写。由此形成一条重要边界：任何文章、缓存、翻译或 schema 变化，都要同步检查 Admin 发布与公开文章回放。

## 2026-07-16—07-18：书本主页的高投入探索

**状态：历史实现；翻页方向已放弃**  
**证据：** `ea4863b`、`8471db0`、`1fb625b`、`f62330b`、`32c37c8`、`9744c43`

Home V2 从一本闭合的数字书开始，逐步加入开发者的话、划词体验、阅读工作台和推荐目录。实现先后经历连续书本空间、整张 DOM 快照纸、软纸弯曲、正反向滚动、目录直达、端点交接和自动收尾。为修复左上角位移、旧页回闪和半途反转，大量几何、时序和状态规则被写入代码与文档。

在当时，翻页的惊艳感是真实的，用户也曾明确希望保护纸张弯曲效果。因此修复它、避免擅自删除并不是错误。真正的问题是验收偏向“状态机是否正确”，没有充分证明“是否达到参考视觉”和“重复使用是否仍然舒服”。参考网站现场浏览又因浏览器运行时失败而没有完成可靠截图/交互验证，但后续知识文件仍把翻页写成了受保护的最终答案。

这个阶段留下两种遗产：一是相当扎实的复杂前端动效调试经验；二是更重要的教训——技术修好不等于视觉还原，更不等于产品适合。

## 2026-07-17—07-26：品牌效果、Menu 与移动端持续打磨

**状态：部分保留，部分待新设计重审**  
**证据：** `dd2187a`、`9744c43`、`bcd31d7` 及同期实现记录

封面加入克制的 Ballpit 球体碰撞，桌面恢复鼠标彩色字母，首页 Menu 承载使用说明、账号与用量、生词本、保存文章、意见反馈和开发者 Admin。菜单预览、生词大列表、局部滚动、移动端点击优先与正式 Reader 的工具面板持续改进。

用户目前明确喜欢封面和球体碰撞，认为它可以成为封面或品牌 IP；其他旧主页表现层，包括鼠标字母、Menu 形态和章节安排，需要放回新的整体设计中判断，不能因为过去实现过就自动永久保留。

## 2026-07-29—08-09：主站迁入中国大陆

**状态：已上线**  
**证据：** `docs/mainland-deployment-and-migration-plan.md`、`ops/mainland/`

正式域名切换到 `context-reader.com`，Next.js、PostgreSQL、Auth、REST、Storage 和内部兼容网关在腾讯云上海运行。迁移保留账号 UUID、权限、用量、公开文章和协议 2 学习同步语义，同时保留 Vercel/托管 Supabase 作为回滚源。

这一阶段还修复了首页推荐正文过早读取造成的流量放大，建立版本化应用发布、只重建 app/caddy、健康检查、数据库备份、恢复验证、推荐定时任务和回滚门槛。Context Reader 从“能部署的网站”进入了“有运营和恢复底座的产品”。

## 2026-08-09：主页方向正式纠偏

**状态：已接受待实现**

用户对当前体验给出了明确判断：书本式翻页与真实阅读场景割裂；翻页速度拖慢进入阅读；滚轮究竟控制页面滚动还是翻页存在语义冲突。最初的惊艳感在重复使用中消退，继续调翻页参数已经不是正确问题。

同时，用户仍然喜欢封面与球体碰撞，认为它有吸引力，适合继续做封面或品牌 IP。新的已确认方向是：

- 保留封面与 Ballpit；
- 舍弃全部翻页与滚轮翻页；
- 点击后快速显示真实推荐文章并进入阅读；
- 推荐区域基于用户确认的 Lusion 参考高保真实现，本站图片略小；
- 不建 `/home-lab`，直接改真实 `/home-v2`；
- UI 第一版就接真实数据、账号、Menu 和 Reader 功能，不再先做外壳后同步功能。

这次讨论还指出了 AI 前端协作的真实成本：用户很难用语言精确描述动效；实现者可能只证明代码正确却没有真正看懂视觉；大重构会消耗大量额度反复调 UI；长文档和记忆会把过期讨论继续注入新会话。新的工作方式因此改成小切片、参考录屏/关键帧、三层验收和用户最终视觉确认。

用户也明确表达了产品态度：自己不满意，就坚决不会给别人用。这不是要追求无穷装饰，而是要求每一次上线都经得起真实、重复的使用。

## 2026-08-10：知识纠偏与产品历程制度建立

**状态：已完成**

项目文档撤销了“翻页是受保护系统”的未来约束，改为同时标注“当前线上仍有旧代码”和“已接受但尚未实现的新方向”。主页验收被拆成技术正确、视觉还原、重复使用体验三道独立门槛；浏览器无法观察时必须明确写未验证，构建或 HTTP 成功不再被当作视觉完成。

同时建立本文件。以后每次完成 UI、功能、基础设施或关键产品决策，都要在对应主文档更新当前状态，并在这里追加一段历程。这样未来既能得到干净、准确的工作上下文，也能在真正完成那天回头看见它是怎样一步步长成的。

## 2026-08-12：确认 I Read World 为内容秩序参考

**状态：已接受待实现**  
**类型：UI / 决策**  
**证据：** `docs/home-v2-implementation-contract.md`

用户明确喜欢 `I Read World | 读外刊·看世界` 的网站 UI，原因是整体风格简洁、清晰，但同时强调这并不代表 Context Reader 应该模仿它。这个参考因此被限定为内容秩序与信息架构证据：外刊品类和核心入口一眼可见，文章内容处于视觉中心，导航数量克制，进入阅读的路径直接。

下一版 Context Reader 可以吸收这种清晰度，但不复制对方的布局、配色、字体、卡片或品牌表达。本站仍要保留封面、Ballpit 与鼠标字母形成的独立第一印象，并用更明确的“开始阅读 / 精选外刊”双入口把品牌表现和真实使用连接起来。

本次未修改产品代码。公开页面结构可以确认，浏览器现场视觉抓取连续超时，因此更细的尺寸、响应式与动效观察仍标记为未完全验证。

## 2026-08-12：Lusion 精选外刊动效取得录屏级规格

**状态：已接受待实现**  
**类型：UI / 决策**  
**证据：** 用户录屏 `屏幕录制 2026-08-12 171544.mp4`、`屏幕录制 2026-08-12 171742.mp4`、`docs/lusion-recommendation-motion-spec.md`

此前虽已把 Lusion 写成推荐展示参考，但现场网页曾无法可靠运行，只能从公开 bundle 推断 Three.js、WebGL 和 DOM/mesh 同步路线。“想要 Lusion 那种感觉”仍然不足以约束形变中心、滚动手感、点击层级和时间顺序，继续直接编码仍有开盲盒风险。

用户提供的两段录屏第一次把目标补成了可逐帧观察的规格：图片边框保持稳定，指针驱动边框内部的局部景深与三维表面；滚轮保持自然页面滚动，图片依据滚动速度产生滞后、拉伸、模糊和回弹；点击后选中图片从原卡片边界抬升、倾斜并占满场景，再溶解为色场，最后分层显现目标内容。

Context Reader 确认复刻这套动效语法，但不复制 Lusion 的品牌与项目详情结构。精选外刊图片会更小，静止信息秩序继续追求 I Read World 式的简洁清晰；点击转场的终点必须是现有真实 `ReaderView`，滚轮永远只负责自然滚动。完整视觉版本应先按录屏节奏实现并由用户验收，是否为了重复使用缩短节奏属于后续产品体验决策，不能在实现前擅自稀释“完整复刻”。

本次只完成了观察、知识纠偏和可验收规范，没有修改产品代码、构建或部署。它把以后 UI 实现的判断依据从“像不像我想象中的 Lusion”改成了“关键帧、层级、速度和回弹是否与录屏一致”。

## 2026-08-12：新老用户路径与首页内容顺序收敛

**状态：部分已接受，视觉形态待选择**  
**类型：产品 / UI / 功能 / 文案决策**  
**证据：** 用户填写的 `Context Reader 产品重设计决策稿`、`docs/home-v2-implementation-contract.md`

用户明确否定了“把你想读的外刊，变成真正读得下去的英语”这一类直白口号，指出许多既有文案虽然意思直接，却缺少美感与斟酌。产品对外表达重新回到语境翻译/语境理解这一主体；精选外刊虽然成为突出入口，但在内容质量尚未稳定前，不承担唯一产品承诺。

产品结构进一步收敛为两条路径。新用户先经过保留 Ballpit 的品牌封面，随后直接看到 5–6 篇可分类切换的精选外刊，再自然进入粘贴正文/输入网址、功能说明和联系反馈。只有登录用户才被视作老用户，优先进入继续阅读、粘贴文章、输入网址和单独查词组成的工作台；封面缩成品牌标识，不重复要求老用户观看完整介绍。

全站导航也形成了新的待验证假设：输入文章、单独查词、生词本和我的文章属于左侧常驻高频入口；账户与用量、使用说明、意见反馈、设置/无障碍和开发者 Admin 属于 Menu。使用说明需要重构并收纳开发者的话和用户主动播放的划词动图；意见反馈既保留在 Menu，也出现在主页末段；新用户可以从 Menu 直接登录。Menu 的具体展开方式、悬停预览是否保留和背景可读性仍需参考优秀产品后再由用户选择。

本轮没有授权实施。封面占比、封面进入精选外刊的专属转场、左侧导航形态、Menu 悬停范围、第一屏文案和功能介绍排版仍属于待选设计，不能因为问卷里出现候选就写成已上线或最终决定。

## 2026-08-12：品牌门面、球幕开孔与全站左栏确认

**状态：已接受待实现；Menu 内容承载方式待选**  
**类型：UI / 动效 / 导航 / 文案决策**  
**证据：** 用户提交的 `Context Reader 本轮视觉选择`、`components/Ballpit.tsx`、`docs/home-v2-implementation-contract.md`

新用户封面被确定为完整品牌门面，约占一屏的大部分高度，同时从底部露出精选外刊的一线内容。封面不再是书，也不成为封闭的介绍页。第一屏文案确认使用“在语境里，读懂英文。”。

封面进入精选外刊的方向确认采用“球幕开孔”：球体在扩大的力场作用下沿真实碰撞关系让出通道，同一个开孔进度揭开封面，使外刊从球幕内部出现。代码检查表明现有 Ballpit 已具备 Three.js 单画布、实例化球体、逐球速度/位置、球体碰撞和一个可推动其他球体的不可见控制球，因此机制具备实现基础；但现有组件尚无转场时间轴、可控开孔中心/半径、遮罩联动和完成交接 API，不能宣称视觉效果已经做成。真正实现仍须小切片、真实浏览器录屏和用户验收。

全站导航确认采用双层左栏：输入文章、单独查词、生词本和我的文章常驻，悬停只提供短提示；账户与用量、使用说明、意见反馈、设置/无障碍和 Admin 留在点击打开的不透明 Menu。文章阅读界面也必须继续保留这条左栏，不能为了“沉浸”让全站导航突然消失。

仍未决定的是每种 Menu 内容的承载方式。长内容、短任务、可边看边调的设置和权限独立的 Admin 不应未经讨论全部塞进同一种弹窗；下一轮将分别比较主工作区、覆盖层、对话框、抽屉和独立路由。

## 2026-08-12：球幕连续性与左侧导航形态纠偏
