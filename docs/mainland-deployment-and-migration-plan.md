# Context Reader 中国大陆部署与数据迁移计划

> 状态：大陆生产切换已完成，`https://context-reader.com` 已通过 HTTPS、首页/Reader、账号登录、协议 2 同步、Admin、重启、备份恢复和镜像回滚验收。  
> Vercel 站点与原托管 Supabase 项目仍完整保留为回滚源，未经用户确认不得删除。托管 Supabase Storage 在导出期间持续返回 402，因此旧环境中的 8 个反馈/错误对象和 879 个发音缓存未复制；它们仍留在旧项目，核心数据库、账号 UUID、权限、用量与学习同步数据已经迁入大陆主库。

## 1. 已确定的决策

- Context Reader 的正式主站最终部署到中国大陆节点，不把中国香港作为主站长期方案。
- 优先控制早期成本，同时保留升级到托管数据库、双机或 CDN 的路径。
- 迁移不是借机重写产品。切流时保持当时已上线的 React 界面、ReaderView、查词、翻译、生词本、Anki、Admin 和本地数据语义；迁移完成后的产品 redesign 是另一条独立工作流，以当前产品契约为准。
- 使用并行环境、数据复制、影子验证、可逆域名切换；不得通过一次性停机搬迁直接替换现网。
- 旧 Vercel 与 Supabase 长期保留为回滚源；任何清理都需要单独确认和已验证的增量数据处理方案。

## 2. Supabase-compatible backend 当前负责什么

生产环境在同一台大陆服务器上运行 PostgreSQL 17、GoTrue Auth、PostgREST、Storage API 和内部网关，继续提供应用已经使用的 Supabase-compatible API。它承担：

1. **账号认证**：手机号被映射为服务端内部邮箱，Supabase Auth 保存密码哈希、签发 access/refresh session。
2. **账号与权限**：用户资料、套餐、Admin entitlement、账号状态。
3. **用量与成本**：游客/注册用户额度、原子扣减、退款、上游执行与成本记录。
4. **跨设备同步**：文章、生词、解释、翻译、阅读状态和偏好对象的版本化同步、冲突合并与 tombstone。
5. **公开内容**：推荐文章、预生成解释、预生成全文翻译。
6. **对象存储**：推荐封面、私有反馈附件、错误报告、云端发音 MP3。

因此这次迁移同时保留了 Auth、PostgreSQL/PostgREST/RPC 和 Storage 三类契约，前端页面和 `/api/*` 无需感知来源变化。

### 迁移结果与尚存限制

- 浏览器仍只访问 Context Reader 自己的域名，不会收到 Supabase key。
- 账号、权限、额度、同步对象和公开文章已按原 UUID、版本与游标语义导入大陆主库。
- 新的封面、反馈、错误和发音缓存写入大陆 Storage；发布推荐时，外部封面会先安全下载并压缩为本站 WebP，访客不再依赖国外图片站。旧托管 Storage 中未能导出的私有历史对象不影响登录与学习数据，发音缓存可在使用时重新生成。
- 首页只加载推荐摘要并使用五分钟服务端缓存，正文只在用户准备打开或实际打开时读取，避免再次出现 31 GB 的响应放大。

## 3. 推荐的低成本最终架构

### 3.1 Beta 起步方案

- 已购买的腾讯云中国大陆轻量应用服务器位于上海，规格为 4 核 4 GB、40 GB SSD、3 Mbps、300 GB/月，首年实付 109 元，到期日为 2027-08-03；服务器自动续费保持关闭，续费前必须重新核对续费价和可迁移替代套餐。
- 已购买 `context-reader.com`，首年实付 83 元；域名自动续费保持开启以避免域名失效或被他人注册，但续费前仍应检查通知与价格。
- Next.js：继续使用当前代码，构建为 standalone 产物或容器，服务端运行 Node.js。
- 反向代理与 TLS：Caddy 或 Nginx；证书自动续期。
- 数据与账号：同机 PostgreSQL 17、GoTrue Auth、PostgREST、Storage API 和内部网关，只监听私有 Docker 网络；浏览器不直连。
- 文件：当前先使用同机 Storage volume，公开封面与私有反馈/错误/发音保持不同 bucket 和权限；COS 尚未购买，作为后续异地副本/扩容选项。
- 当前备份：服务器每日生成 PostgreSQL 自定义格式备份和 SHA-256，日备份保留 7 天、周备份保留 35 天、月备份保留 370 天；每周从备份真实恢复到一次性校验库。开发电脑每天 04:45 和每次 Windows 登录时尝试拉取一份异地压缩包，若本地已有 20 小时内的新备份则跳过，因此电脑在 04:45 关机不会漏掉服务器备份。COS 尚未购买，公开上线或出现真实用户数据前再配置第二个云端异地副本。
- 定时任务：systemd timer 每五分钟唤醒一次 `/api/cron/recommendations`，应用按 Admin 中保存的北京时间、开关和每次 1–6 篇上限判断是否到点；同一天只成功执行一次，只新增待审核候选，不自动发布，成功后向站点通知邮箱发送摘要。
- 日志：应用日志按天轮转；错误详情仍只进入私有 Admin 存储。
- 版本发布：生产候选必须来自当前接受版本之上的干净 Git 集成提交，并由 `ops/mainland/package-release.py` 写入父版本、源码提交和精确改动清单。服务器只调用候选包之外的稳定 `/opt/context-reader/bin/deploy-release`，以全局锁串行发布，拒绝父版本过期、改动清单不符或丢失累计保护契约的包；候选容器验收后再只以 `--no-deps` 重建 `app` 与 `caddy`。常规代码发布不得连带重建 PostgreSQL、Auth、REST、Storage 或内部网关；否则会制造无必要的数据库重启和短暂中断。完整并行协作与恢复制度见 `docs/release-governance.md`。

当前首年固定成本为服务器 109 元 + 域名 83 元，共 192 元，折合约 16 元/月；这是首年活动价，不是续费承诺。COS 尚未购买，DeepSeek、火山 TTS 等上游费用仍按真实用量计算。若产品没有做起来，可在服务器到期前导出已验证备份并停止续费；若已有用户，则在到期前至少 30 天比较续费价、同云迁移和跨云迁移，保持 Docker、标准 PostgreSQL 备份和域名 DNS 分离可以避免被单一套餐锁定。

### 3.2 为什么不一开始买腾讯云托管 PostgreSQL

托管 PostgreSQL 提供高可用、自动备份和运维托管，但公开目录价明显高于一台轻量服务器。Beta 阶段若用户量小，先自托管 PostgreSQL + 异地 COS 备份能显著控制成本。

出现以下任一情况时升级托管数据库：

- 可接受的恢复点目标低于 15 分钟；
- 单机故障不能接受；
- 日活或写入量持续增长；
- 数据库内存压力与 Next.js/AI 请求互相影响；
- 已开始收费或承诺服务可用性；
- 维护、备份和安全更新的人力成本高于托管费用。

### 3.3 为什么当前保留 Supabase-compatible 多服务

最终验收选择了 PostgreSQL、GoTrue、PostgREST、Storage 和网关的兼容组合，因为它能原样保留已有账号 UUID、密码验证、RPC、Storage bucket 和服务端数据路径，迁移风险低于同时重写账号与数据适配器。它不是浏览器可直接访问的完整 Supabase Studio/Realtime 平台；所有服务只在私有网络中运行，由 Docker 健康检查、systemd 监控和版本化发布管理。资源增长或开始收费后，再评估托管 PostgreSQL、COS 和分布式限流。

## 4. ICP 备案：准备什么、在哪里办、怎么申请

以下以腾讯云为推荐操作路径。若最后选择阿里云，原则相同，但应在阿里云备案系统提交，备案接入商必须与大陆服务器接入商一致。

### 4.1 先确定备案主体

#### 个人备案

适合个人、非经营性、尚未收费的测试型网站。准备：

- 中国大陆居民身份证原件；
- 本人常用大陆手机号和邮箱；
- 实际通信地址；
- 已由本人实名认证的可备案域名；
- 部分省份要求的居住证、暂住证、学生证、社保或工作证明；
- 管局要求时的网站建设方案书。

个人备案的网站名称和内容必须符合所在省管局的个人网站规则。不要为了通过审核而填写与实际产品明显不一致的信息。

#### 单位/企业备案

若近期计划公开经营、收费、签约、宣传为正式商业产品，优先使用单位主体。准备：

- 营业执照或对应单位有效证件原件；
- 法定代表人身份证；
- 主体负责人和网站负责人的身份证、手机号、邮箱；
- 网站负责人不是法定代表人时的授权书；
- 已由同一单位实名认证的域名；
- 部分省份要求的域名证书、建设方案书或其他补充材料；
- 若内容涉及新闻、出版、教育、医疗、文化、视听等受专项监管领域，按真实业务确认是否需要前置审批。

域名所有者、备案主体和云账号实名信息应尽量从一开始保持一致，避免后续变更主体。

### 4.2 注册并实名认证域名

建议：

- 在最终服务器同一家云厂商注册，简化实名认证和备案材料；
- 优先选 `.com` 或 `.cn` 等明确可备案后缀；
- 不使用 `vercel.app` 子域名备案；
- 注册前确认域名没有残留旧备案或不良历史；
- 域名实名主体必须与 ICP 主体一致；
- 腾讯云域名实名认证通过后通常需等待至少 3 个自然日才能提交腾讯云备案；外部注册商域名可能需 3 个工作日并提供实名截图。

操作入口：

1. 腾讯云控制台 → 域名注册；
2. 创建个人或企业实名信息模板；
3. 查询并购买域名；
4. 关联已审核的实名模板；
5. 等待实名认证和命名审核完成；
6. 下载并保存域名证书。

### 4.3 购买符合备案条件的大陆资源

腾讯云备案资源建议选择：

- 中国大陆地域，不选中国香港或境外；
- 包年包月；
- 累计购买至少 3 个月；
- 备案期间剩余有效期至少 1 个月；
- 公网 IP；
- 公网带宽不为 0。

地域优先按主要用户和备案/运维便利选择。数据库、COS 和服务器尽量同地域，避免额外时延和流量费。

### 4.4 提交首次备案

入口：

- 腾讯云控制台搜索“网站备案”或“ICP 备案”；
- 也可从腾讯云备案小程序继续材料上传和人脸核验。

顺序：

1. 选择“首次备案”。
2. 选择备案省份和个人/单位性质。
3. 选择刚购买的合规轻量服务器作为备案资源。
4. 填写主体名称、证件号码、证件地址、通信地址、手机号、邮箱。
5. 应用服务类型选择“网站/域名”。
6. 填写网站名称、域名、语言、服务内容和备注。
7. 如实选择前置审批情况；不涉及才选择“不涉及”。
8. 填写网站负责人并上传身份证原件照片。
9. 用中国大陆手机号实名微信完成视频/人脸核验；核验定位通常需与备案省份要求一致。
10. 上传省管局要求的域名证书、授权书、居住证明或建设方案书。
11. 提交腾讯云初审；保持电话畅通并及时按审核意见修改。
12. 收到工信部短信后，在规定时间内完成短信核验。
13. 等待省通信管理局审核。

材料齐全后，法规规定管局可在 20 个工作日内完成审核；云厂商初审、材料修改和短信核验时间不包含在这个理想值中，因此计划上应预留 2–4 周。

### 4.5 备案通过后

1. 在网站首页底部展示 ICP 备案号。
2. 备案号链接到工信部备案系统。
3. 配置域名 DNS、HTTPS 和自动续期。
4. 按适用要求完成公安联网备案；不要把 ICP 备案与公安备案当成同一件事。
5. 发布隐私政策、用户协议、账号注销/数据导出说明。
6. 核实 DeepSeek 等生成式 AI 服务的备案/登记信息和产品内公示要求。
7. 如果以后收费，再单独核实经营性 ICP、支付、税务、消费者权益和退款规则；非经营性 ICP 备案不等于取得经营性 ICP 许可证。

## 5. 用户必须亲自完成与 Codex 可以完成的边界

### 用户必须完成

- 决定个人还是单位备案主体；
- 提供真实省份、证件、手机号、邮箱和主体材料；
- 购买云账号、域名、服务器和必要服务；
- 完成账号/域名实名认证；
- 完成人脸、短信和电话核验；
- 对备案信息和业务性质作最终确认；
- 在云控制台授权临时、最小权限的部署/迁移凭据。

### Codex 可以完成

- 根据所选云厂商生成逐屏操作清单；
- 审核服务器规格和成本；
- 配置服务器、Docker、反向代理、TLS、防火墙和监控；
- 实现 PostgreSQL/Auth/COS 适配层；
- 编写数据导出、校验、导入和回滚脚本；
- 搭建大陆影子环境；
- 运行功能、视觉、性能、数据一致性和安全回归；
- 执行分阶段切流、观察和回滚；
- 在迁移完成后对齐 README、架构、集成指南、AGENTS 和记忆。

Codex 不能替用户冒充身份、支付购买、接听审核电话或完成人脸/短信验证。

## 6. 不破坏现有界面的迁移策略

### 6.1 代码隔离原则

基础设施迁移本身不得重写这些前端能力。下列是切流时的回归基线，不是对后续产品 redesign 的永久限制：

- 当时上线的主页入口与推荐/Reader 连接；
- `ReaderView` 阅读、编辑、undo/redo 与图片查看；
- `ExplanationPanel` 流式解释布局；
- `ArticleTranslationPanel` 后台翻译任务；
- 生词本、Anki 模板、Menu 预览与移动端手势。

改动集中在服务端适配层：

- `lib/userAuth.ts`
- `lib/accountStore.ts`
- `lib/publicArticles.ts`
- `lib/feedbackStore.ts`
- `lib/errorReportStore.ts`
- `lib/pronunciationServer.ts`
- `app/api/admin/article-covers/route.ts`

对浏览器保持原有 `/api/*` 请求与响应结构，组件无需知道数据来自 Supabase、PostgreSQL 还是 COS。

### 6.2 必须先建立的适配边界

引入显式后端模式：

```text
DATA_BACKEND=supabase | dual | mainland
AUTH_BACKEND=supabase | bridge | mainland
STORAGE_BACKEND=supabase | dual | cos
```

每个后端实现同一接口，并保留运行时快速切回 Supabase 的开关。迁移期间所有破坏性数据库操作必须禁止。

## 7. 分阶段迁移

### 阶段 0：建立生产基线

- 给当前稳定提交打 Git tag，记录 Vercel deployment id。
- 导出当前环境变量名称清单，不导出到仓库。
- 对生产数据库做全量备份；对象存储列出全部 key、大小和哈希。
- 保存主要页面桌面/移动截图和关键交互录像。
- 建立当前接口契约样本与回归测试。
- 记录 Supabase 各表行数、用户数、对象数、最新版本和 tombstone 数。
- 固化当前同步协议样本：protocol 2 的 active/deleted bootstrap、opaque cursor 增量页、CAS 冲突、手动进度反馈，以及约 800 ms 本地上传、15 秒可见页拉取和 focus/visibility 拉取。

### 阶段 1：大陆空环境

- 部署同一 Git commit，不改 UI。
- 暂时仍连接现有 Supabase。
- 使用测试域名或 hosts 文件访问，绝不先改正式 DNS。
- 测量大陆服务器到 Supabase、DeepSeek、火山 TTS、国外 RSS/文章源的真实质量。
- 验证反向代理传递真实 IP，避免限流把所有用户当作一个 IP。

如果这一步体验稳定，可以先上线大陆应用 + Supabase，数据库迁移作为第二阶段；这样可显著降低一次迁移的变量数量。

### 阶段 2：大陆 PostgreSQL 兼容层

- 把现有 Supabase SQL 迁为标准 PostgreSQL schema。
- 保留所有 UUID、时间戳、JSONB、server_version、tombstone 和唯一约束。
- 保留 `user_data_objects(user_id, updated_at, kind, object_key)` 的稳定排序与等价索引；大陆实现必须支持以该复合键做 keyset 增量读取。
- 把 `consume_usage`、`refund_usage`、`finalize_usage`、`merge_user_data_objects` 等 RPC 原子语义原样迁移。
- 通过数据库适配器替换 PostgREST URL 拼接，浏览器 API 不变：首次只传 active payload 和轻量 tombstone 索引，之后只传 cursor 之后的变化；迁移期继续兼容旧 offset 读取，但新客户端不得退回每次全量扫描。
- 先只做影子读：同时读取两边并比较，不把新结果返回给用户。

### 阶段 3：数据全量复制

- 在一致性时间点导出 Supabase 业务表。
- 按外键顺序导入大陆 PostgreSQL。
- 对每张表校验行数、主键集合、关键 JSON 哈希、最大更新时间。
- 对 `user_data_objects` 额外校验 `kind + object_key + server_version + deleted_at`。
- 用真实大账号对比 bootstrap 总数、active 数、tombstone 数、最终 cursor 和随后零变化增量页；两端结果必须一致。
- 不删除 Supabase 数据。

墓碑压缩不属于本次搬迁的前置步骤。只有在大陆端稳定运行、定义删除保留期，并能证明所有活跃客户端都已确认超过某个高水位后，才单独设计 GC；不得因为墓碑数量大就直接批量删除。

### 阶段 4：Auth 迁移

Supabase Auth 的密码哈希不能假设可直接导出。推荐使用“登录时再哈希”桥接：

1. 保留原 Supabase user UUID。
2. 迁移用户元数据和账号表，不迁移不可得的密码哈希。
3. 迁移期用户登录时，先由 Supabase 验证原密码。
4. 验证成功后，在大陆 Auth 表用 Argon2id 或等价安全算法重新哈希同一次用户输入。
5. 签发 Context Reader 自己的 HttpOnly session，同时标记该账号已迁移。
6. 新注册账号直接创建大陆凭据；桥接期按需双写最小身份映射。
7. 长期未登录账号继续保留 Supabase fallback，或由 Admin 走现有临时密码流程。

整个过程不得记录明文 PIN，不得把内部 synthetic email 暴露给用户。

### 阶段 5：Storage 迁移

- 推荐封面复制到公开 COS bucket。
- 反馈附件、错误记录、发音 MP3 复制到私有 bucket。
- 保留逻辑 key；逐对象比较大小、Content-Type 和 SHA-256。
- 私有对象只允许服务端读取或生成短时签名 URL。
- 迁移期先读 COS，缺失时回退 Supabase，并异步补齐。
- 对外 URL 不批量一次性替换，避免旧文章封面全部失效。

### 阶段 6：双写和影子验证

- 新写入同时进入大陆库和 Supabase。
- 主响应只依赖当前主库；副库失败写入持久重试队列，不能拖死用户请求。
- 每日比较表行数、关键哈希、额度计数、同步版本和对象数量。
- 只有连续 7 天没有未解释差异，才能进入切流。

### 阶段 7：域名与用户数据迁移

新域名会产生新的浏览器 origin：

- `localStorage` 不会自动从 `vercel.app` 跟到新域名；
- Cookie 和登录状态不会自动迁移；
- PWA/Service Worker 也不会跨域迁移；
- AnkiConnect CORS 需要加入新域名。

措施：

1. 已登录用户：旧站先完成最终云同步；新站登录后从云端恢复。
2. 游客：旧站提供明确的“迁移本机数据”导出/导入，或经严格 origin 校验的一次性迁移码。
3. 旧站提前显示迁移提示和截止日期，不立即强制跳转。
4. Anki 指南同时允许旧、新两个 origin，稳定期后再移除旧 origin。
5. 新域名重新安装 PWA；旧 PWA 提示用户打开新站。

### 阶段 8：灰度切流

- DNS TTL 提前降至 300 秒。
- 先由开发者和白名单测试账号使用新域名。
- 再扩大到少量邀请用户。
- 检查错误率、p95、登录成功率、同步冲突、AI 完成率、内存、磁盘和数据库连接。
- 正式切换后至少保留 Vercel/Supabase 30 天只读回滚能力。

## 9. 大陆部署特有风险与措施

### 国外文章和 RSS

大陆服务器访问 NASA、NPR、Aeon 等国外来源可能变慢或失败。措施：

- 先对现有白名单逐站实测；
- crawler 单源失败继续隔离；
- 为导入和 crawler 保留受控的境外抓取 fallback，仅传输公开文章，不承载账号或私有数据；
- 或逐步增加大陆稳定可访问且版权边界清楚的来源；
- URL 导入结果继续经过现有 SSRF、DNS pin 和正文边界清理。

### 远程图片

国外图片可能很慢，也可能禁止其他网站直接引用。措施：

- 候选保存时只记录审核过的外部地址，避免抓取任务被超大图片阻塞；
- 发布公开推荐时经固定 DNS 的安全抓取、图片类型和大小校验，把封面裁切压缩成 1280×800 WebP 并复制到当前大陆 `public-article-covers` Storage；将来启用 COS 时保持同一接口；
- 历史外部封面使用受保护的 Admin 维护接口定点修复；页面仍保留友好的坏图占位；
- 对正文图片先实测，必要时在导入时复制有意义图片并保留来源归属；
- 不把导航、广告或站点 chrome 图片批量搬入。

### 单机故障

- 数据库不开放公网端口；
- 每日异地备份；
- 每月从空库实际恢复一次；
- 服务器故障时可重建应用并从 COS 恢复；
- 收费或用户增长后升级托管数据库/双机。

### 磁盘、内存和连接

- 2 核 4 GB 不在生产服务器现场执行重型并发构建；
- 使用 CI 或受控构建产物；
- Node、PostgreSQL 和日志设置明确内存/磁盘上限；
- 磁盘 70%/85% 两级告警；
- 数据库连接池设硬上限；
- AI 并发继续受成本闸门保护。

### 安全

- 私有影子阶段公网仅开放受限 SSH；ICP 备案通过并准备公开验收时才开放 80/443；
- SSH 密钥登录，禁止密码和 root 直接登录；
- 定期安装安全更新；
- secret 只进入服务器 secret store/环境文件，不进镜像和 Git；
- COS 私有 bucket 默认拒绝公开；
- 备份加密并定期验证；
- Admin、同源写入、HttpOnly cookie、SSRF 和 body limit 规则保持。

## 10. 回滚条件

出现以下任一情况立即停止扩大流量并回滚：

- 登录/刷新失败率超过基线 1 个百分点；
- 任一数据表出现无法解释的主键或版本差异；
- 用户文章、生词或缓存出现丢失/重复；
- 首页或 Reader 核心视觉回归未通过；
- AI 请求错误率或 p95 连续 15 分钟显著恶化；
- 数据库磁盘、连接或内存进入危险阈值；
- Admin 权限、私有附件或对象存储出现越权。

回滚动作：

1. 先停止大陆端新的写入，保留日志、容器镜像和数据库快照。
2. 导出并校验大陆端自切换以来的增量；托管 Supabase 不是自动双写副本，不能跳过这一步直接丢弃新数据。
3. 紧急只读访问可先使用保留的 Vercel 地址；需要让自有域名回到 Vercel 时，先完成 Vercel 域名绑定再改 DNS。
4. 将经过审计的增量恢复/合并到托管 Supabase，验证账号与同步后再恢复写入。
5. 不删除任何大陆表、托管 Supabase 表/Auth 用户/Storage 对象、旧域名或已接受镜像。
