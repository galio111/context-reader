# Context Reader Architecture

## Overview

Context Reader is a Next.js app with a client-side reading workspace and server-side AI/helper routes. The app supports three article entry modes:

- Plain text paste: stores and renders text only.
- URL import: server extracts public HTML into structured blocks, then the reader renders headings, paragraphs, lists, quotes, images, and inline upper/lower annotations.
- Homepage image reading: uploaded screenshots/scans run text OCR and layout-word detection in parallel, preserve the source image, and open as a readable image article. Automatic OCR for images embedded in URL imports remains disabled in the reader.

## Reading Flow

`app/page.tsx` server-loads public recommendations and passes them to `HomeClient`, which owns the active article and home/reader state. Plain text articles pass only `article` into `ReaderView`. URL imports also pass `importedArticle`, which contains rich `blocks`. A text block's plain `text` remains the source for lookup, summaries, copying, and saved article identity; optional `inline` segments preserve visual annotations such as original `sup` and `sub` text. Image blocks render as article media with a click-to-enlarge zoom viewer. The viewer uses wheel zoom anchored at the cursor position, blocks background scrolling, exposes a download action, and renders clickable overlays when `layoutWords` are stored.

Homepage image uploads are a separate path from URL-imported article images. `HomeClient` calls `/api/ocr-image` and `/api/ocr-image-layout` in parallel, uses layout text as a fallback if plain OCR fails, stores the uploaded image as a data URL, and retains any detected `layoutWords` or `layoutError`. Plain OCR text remains the article body for saving and summaries, while the image viewer uses word boxes for click-to-explain. `ReaderView` keeps `IMAGE_OCR_ENABLED = false`, so it does not automatically OCR arbitrary images embedded in URL imports; existing `ocrText` remains backward-compatible data. `ReaderView` tokenizes text blocks so word selection, phrase dragging, cached explanations, vocabulary saving, CSV export, and Anki import work across plain and URL-imported articles.

Saved articles live in browser `localStorage` through `lib/articles.ts`. `SavedArticle.importedArticle` is optional for backward compatibility. When present, reopening a saved URL import restores the original structured layout, images, supported inline annotations, and any OCR text already attached to image blocks instead of falling back to plain text.

`components/PronunciationButtons.tsx` provides compact US/UK playback controls for explanations and vocabulary entries. It uses browser `SpeechSynthesis` with `en-US` and `en-GB` voices at a steady rate and hides itself when the browser does not support speech synthesis.

## Article Editing

`ReaderView` edits article text in place rather than replacing the article with a textarea or a separate block editor. Read and edit states share `textBlockClassName`, so entering edit mode must preserve the same font size, line height, tracking, width, wrapping, and paragraph margins. Word lookup is disabled while editing. The toolbar provides global article undo and redo for the current reading session, not browser-native `execCommand` undo/redo. The history starts when the reader opens and remains available across edit mode and saved states until the user returns to the homepage. Imported article images are displayed but are not editable or uploadable; edit mode can remove an image block through the image's top-right delete button.

Plain text uses one `contentEditable` root containing the rendered paragraph elements. Imported articles also edit text blocks directly in the reading canvas while keeping image blocks read-only. Input events update the session history but still do not control the editable DOM on every keystroke, because rerendering controlled editable content moves the caret to the start. Save reads direct child text through `textContent`, normalizes non-breaking spaces, preserves explicit blank paragraphs as durable content, and serializes paragraphs deterministically. A no-op save exits without rewriting the article.

Imported articles edit each text block in place and rebuild `ImportedArticle` only when text actually changes. Empty accidental list-item blocks are removed on save, durable blank non-list paragraphs are preserved, image blocks are retained unless explicitly deleted, and an edited inline block drops its original `inline` segments when the new plain text no longer matches them. `lib/articles.ts::saveEditedArticle` preserves the saved article id, summary, creation time, and Anki-related local data while updating the body, title, rich blocks, and `updatedAt`.

Opening a saved article calls `touchSavedArticle`, refreshes `updatedAt` and the dedicated optional `lastOpenedAt`, and moves it to the front of the local array. `lib/savedArticleMerge.ts` collapses identical bodies and legacy `-local-recovered-*` lineages into one canonical original article, keeps the richest durable payload, carries forward the newest open/update time, and emits tombstones for every discarded id. The homepage saved-article menu therefore renders each logical article once and sorts by `lastOpenedAt`, falling back to legacy `updatedAt` and `createdAt` values. The reading-view vocabulary drawer can resolve a source sentence against all saved articles; when the match is outside the current article, `HomeClient` starts a fresh reader session with that article before highlighting the source, preventing stale article state from consuming the jump request. Long articles use `content-visibility` with remembered intrinsic block sizes to keep normal scrolling responsive. Source jumps carry a monotonically increasing request id, retry until the target tokens exist, materialize the target block, and center it instantly without animating across the document. Imported image blocks persist source width and height when available so the browser reserves their aspect ratio before download. During a source jump, preceding legacy images without dimensions are promoted from lazy loading and their load/error layout events keep the target sentence centered for a short stabilization window. Location highlighting is presentation-only: the source sentence receives a quiet highlight and the selected vocabulary word or phrase receives a stronger amber underline treatment without focus changes, article edits, history entries, or cache-key changes.

## Translation Flow

Sentence context uses punctuation-aware boundary scanning so periods inside common abbreviations, names and initials, numbers, numbered labels, domains, email addresses, and similar dot-joined tokens do not split lookup context prematurely.

Word and phrase lookups send only the selected text plus current, previous, and next sentence context to `/api/explain-word` and, on cache misses, `/api/explain-word-stream` in parallel. The stream uses fixed labels for lemma, phonetic, part of speech, difficulty, meanings, sentence translation, usage, collocations, and examples. `ExplanationPanel` parses those labels into one progressive visual tree. When both requests complete, `lib/explanationDisplay.ts` merges the stream's visible fields into the structured response, caches that merged explanation by `word + sentence`, and keeps the completed stream text rendered. The structured response contributes hidden fields such as Anki metadata; it does not replace the visible stream. Cache replay formats the merged fields back into the same fixed-label text, preserving content, order, spacing, and wrapping. `scrollbar-gutter: stable` prevents action controls from triggering width reflow. Collocations include parenthesized Chinese translations. Repeated taps do not restart an in-flight lookup; the circular regenerate control forces a new result and, when the same `word + sourceSentence` exists in vocabulary, replaces its generated fields while preserving id, creation time, and Anki import status.

Full-article translation uses `/api/translate-article` and appears in the reading view's right sidebar. Users start it from inside that sidebar; there is no top-bar full-translation button and entering the sidebar does not auto-start translation. The client derives translation blocks through `lib/articleTranslationBlocks.ts`, requests one text block at a time, appends each completed translation to the sidebar as it returns, and stores both the merged article result and reusable per-block entries in `localStorage`. After article editing, unchanged block keys reuse their cached translations while changed blocks are marked stale; “更新已修改部分” requests only those changed blocks. Keep the batch size at one block unless there is a deliberate UX tradeoff, because the first translated paragraph should appear as soon as it is ready and later paragraphs should continue appearing after it. Each translation request can include the full current article as `contextBlocks`, so one-block requests still give the model article-level context. Switching back to word explanations must not abort the in-flight translation. After a translation has been requested, reopening the sidebar shows current progress or cache; the circular regenerate button forces a complete new translation of all current text blocks, sends the full article context, and must not reuse old whole-article or per-block translations for the regenerated result. `lib/articleTranslationJobs.ts` estimates remaining time from elapsed time and completed blocks.

## Homepage

`ArticleInput` keeps the existing data and action contract but delegates the visible homepage to `ImmersiveHome`. The homepage opens with a compact paste/URL entry, a clickable sentence demo, and a top saved-article menu that opens by hover, keyboard focus, or click. The menu renders the complete saved list inside a bounded local scroller, orders it by latest open time, supports article deletion, and remains usable as a click-controlled panel on touch devices. The later flow uses a sticky phrase-selection lesson, a recommendation-only third screen, and a final paste/URL entry. Long pasted text stays in the compact first-screen control; hovering or focusing it on desktop reveals a larger scrollable preview without changing the entry bar's height. Empty entry actions are silent. The phrase lesson reveals its prepared example before exposing practice rows; page scroll drives the practice list, and deliberate horizontal dragging reveals each phrase meaning directly below the selected phrase. Desktop wheel input near a scene boundary accelerates and locks into the adjacent screen in either direction; reverse navigation lands on the previous section's last complete viewport, while mobile keeps normal vertical page scrolling. Returning from `ReaderView` mounts the homepage at the top with the word and phrase demos already complete and omits the first-visit loader. The shared vocabulary notebook still opens as a centered dialog.

`app/home-v2/page.tsx` is an independently reviewable continuous book-space route in the same Next.js deployment. It server-loads the same public-article payload and renders `HomeClient` with `homeVariant="book"`; `HomeClient` retains the active article, cache preload, saved-article, vocabulary-source, and `ReaderView` boundaries. `BookHome` owns one fixed book scene and a small state machine: `workbench`, `dictionary`, `preferences`, and `recommendations`. The initial closed hardback opens only after a user click. The workbench uses a real tokenized micro article with the shared explanation panel; paste, URL, and standalone lookup are equal modes; the latest saved article remains conditional. The dictionary is a page-turn branch, not a separate vertical section. Native page scroll drives the fixed book from the workbench into a preference insert and then the recommendation catalogue, while reduced-motion uses short state changes. Reader entry is delayed only long enough for the page or recommendation-cover expansion, then mounts the existing `ReaderView`; returning restores `/home-v2`. Homepage image upload remains intentionally absent, and `/` remains the shipped homepage until approval. See `docs/home-v2-implementation-contract.md` for the authoritative interaction contract.

`BookDictionary` calls `/api/dictionary`, which uses the existing DeepSeek model defaults, disabled thinking mode, concurrency guard, guest/account lookup quota, execution ledger, and estimated-cost recording. Results include IPA, senses, usage distinctions, collocations, word family, synonyms, common mistakes, and a memory hint; the browser keeps a bounded local result cache. `BookRecommendations` receives the server-rendered `initialPublicArticles`, rejects recommendations without the required cover, filters by the learner's selected Chinese learning stage, prefetches article details, and expands the clicked cover before calling the existing public-article-to-ReaderView flow. When the published inventory is empty it shows an explicit inventory state rather than fabricated articles. `/api/feedback` validates same-origin bounded input and stores JSON feedback objects in the private `context-reader-feedback` Supabase Storage bucket. Desktop home-only cursor letters reuse the original colored density and render above both the closed cover and opened pages; a canvas mask removes them around marked article, explanation and form regions, overlays pause the field, and `ReaderView` unmounts it. Mobile has no persistent ambient letters and emits only a small touch ripple.

Public recommended articles are fetched in the server `app/page.tsx` and passed into the client homepage as `initialPublicArticles`. Do not move this list back to a client-only `useEffect` fetch; otherwise the recommendation screen first renders without them and visibly fills them in later. The sticky third screen is exclusively for these recommendations; saved articles belong only to the first-screen top menu.

The reading view uses the same vocabulary data but keeps the notebook as a right-side drawer so it does not cover the article workspace. Both notebook placements lock the underlying page at its current scroll position while preserving an explicitly sized, `min-height: 0` internal scroller for the notebook. The homepage's global wheel/touch teaching locks and desktop scene snapping must ignore events from marked local-scroll surfaces, and notebook overscroll stays contained instead of reaching the page. Vocabulary entries use TanStack Virtual with stable entry keys, transform positioning, bounded overscan, and live element measurement, so even very large notebooks mount only the rows near the viewport while preserving real card heights. Do not reintroduce fixed oversized rows or React state updates on every scroll event; short cards should stay compact and long cards should remain fully visible.

Shared tool panels should not preserve stale interaction traces across open/close cycles. `VocabularyPanel` clears its search, preview, and expanded-detail state and scrolls its list to the top when opened or when the filtered list changes. Vocabulary rows always show IPA when available plus the original core fields; usage notes, collocations, and bilingual examples are progressively disclosed by the per-entry `显示全文` control. Rows continue to use measured content heights before and after expansion. Browser TTS voice discovery and warmup are shared across all pronunciation controls rather than repeated when virtual rows mount. Parent views clear temporary vocabulary errors and Anki status when the drawer/dialog closes.

## Mobile Reader

The mobile explanation panel is a bottom sheet. It defaults to half the viewport height and can be resized with the small top handle. Only the compact collapse button should stay visible while the explanation content scrolls.

Touch word selection separates reading scroll from lookup gestures. Vertical movement is treated as article scrolling and should not highlight or query a word. A tap explains one word. Horizontal movement across words or long-press selection can select a short phrase, capped at eight words.

Each new explanation resets the bottom sheet to its default half-height and scrolls the explanation content to the top. Collapsing the explanation panel should preserve the article reading position, but temporary panel state should not leak into the next lookup.

## Account, usage, and sync

Account sync transport uses byte-bounded response pages, and continues paging past Supabase's default 1,000-row limit up to the route's 20,000-object cap. Automatic learning-data sync is disabled on `/admin`; normal pages serialize writes both within one tab and across tabs with the Web Locks API.

`AccountProvider` loads `/api/auth/session`, opens the phone/password form only for restricted actions, schedules cloud sync after durable local changes, and requires a successful final sync before explicit logout clears browser data. Phone registration collects a nickname, maps the unverified mainland-China phone identifier to a reserved server-only Auth email, and stores the six-digit numeric password through Supabase's password hashing. Legacy email-link adoption remains compatible but is hidden from the current UI. `lib/accountSyncClient.ts` stores each article, vocabulary entry and cache item as a versioned object. Server reads page through all account objects instead of relying on Supabase's default 1,000-row response cap. Supabase compare-and-swap prevents stale devices from overwriting newer versions; client writes are single-flight, unique by kind plus object key, and retry against a fresh complete version list. The client compares normalized JSON payloads with stable key ordering and skips unchanged objects. Article conflicts resolve to one canonical article and discarded duplicate ids become tombstones; article sync must never create a visible recovery copy. The sync API also converts any legacy `-local-recovered-*` article write into a tombstone so an older open tab cannot resurrect deleted copies. After a cloud merge, `HomeClient` refreshes its saved-article state from durable storage immediately instead of showing a stale pre-sync count until reload. Vocabulary versions are normalized, merged and deduplicated by word plus source sentence; redundant recovery ids become tombstones, while a genuinely ambiguous same-id/different-identity local value is preserved in a separate local recovery store and never counted as a notebook entry. Article and vocabulary deletions are persisted as tombstones so another device cannot silently restore them.

Saving an article commits the local article object and schedules account sync before requesting its generated Chinese list summary. Summary or provider failures therefore leave the article saved and retryable instead of rolling back the durable article record.

All cost-bearing routes use `lib/usageGate.ts`. Structured and streaming word lookup requests share `x-context-action-id`, so the quota action is idempotent while `usage_executions` stores both real upstream calls. Registered-user failures are refunded and cache hits are free; guest cached lookups call `/api/usage/cache-lookup`. Full translation, summaries, sentence questions and OCR require login. `/account/usage` is the user view; the unified `/admin` console manages public recommendations, users, ordinary-user limits, provider cost summaries, and feedback. Admin quota rows are grouped by Chinese product meaning, batch-save the fixed metric/window pairs for each ordinary plan, and intentionally hide the developer allowance plus unconnected price settings.

The browser never receives a Supabase key. Without account infrastructure, reading and a browser-enforced ten-lookup fallback remain available, while login and authenticated high-cost features remain disabled.

## API Routes

`middleware.ts` and `lib/requestSecurity.ts` form the common request gate. They apply trusted Vercel IP extraction, route-specific fixed-window limits, daily costly-operation limits, `413` early rejection, same-origin admin checks, request ids, and private admin cache headers. `lib/limitedBody.ts` also counts actual streamed bytes before JSON or multipart parsing, so missing or forged `Content-Length` cannot bypass route limits. `lib/costConcurrency.ts` caps simultaneous AI and OCR work per server instance and releases leases on completion, error, stream cancellation, or client disconnect where the upstream route exposes a signal.

All user-controlled outbound URL reads use `lib/safeRemoteFetch.ts`. It accepts only standard-port HTTP(S), rejects credentials and non-public/reserved IP ranges, resolves and pins the verified IP for the actual TCP/TLS connection, preserves the original Host/SNI, rechecks every redirect, and streams responses through hard byte caps. AnkiConnect accepts only local `127.0.0.1:8765` and has an eight-second timeout.

- `/api/public-articles`: lists public recommended articles for clients and service-worker caching. The homepage does not depend on a client-side call for first paint.
- `/api/public-articles/[id]`: reads one public article plus its preloaded word explanations and full-article translation caches.
- `/api/auth/*`: registers/signs in phone + numeric-password accounts, retains legacy email OTP and hosted-session adoption, reads/refreshes the current account session, and logs out through server-managed cookies.
- `/api/account/sync`: reads and compare-and-swap merges versioned account objects; `/api/account/export` returns the member's profile, synced objects, and usage-action history.
- `/api/usage/cache-lookup`: records cached guest lookups as trial usage without charging authenticated cache hits.
- `/api/admin/*`: handles administrator login, public article listing/publishing/deletion, account/quota administration, and private feedback listing/status/deletion. Writes require the admin session cookie.
- `/api/import-url`: fetches public HTML, strips noisy elements, extracts article-like content, removes embedded personalization/follow/alert modules, normalizes image URLs, preserves `sup`/`sub` inline segments, and returns `ImportedArticle`. Standalone advertisement labels are removed unless the surrounding article is itself substantively about advertising.
- `/api/ocr-image`: extracts text from one uploaded image up to 8MB.
- `/api/ocr-image-layout`: detects word boxes for multipart uploads, data URLs, or remote image URLs and returns percentage coordinates plus line context.
- `/api/ocr-image-url`: extracts text from a remote image URL. The route is enabled, but the URL-import reader does not call it automatically while its OCR gate is off.
- `/api/download-image`: fetches and validates a remote image up to 20MB and returns it as a short-lived private attachment.
- `/api/explain-word`: sends only selected word/phrase and sentence context to DeepSeek.
- `/api/explain-word-stream`: sends the same selected context to DeepSeek and streams fixed-label Chinese text whose completed visible fields are merged into the durable explanation.
- `/api/translate-article`: translates sanitized article text blocks to Chinese for the full-article translation sidebar. The client requests one text block at a time so the first completed block can render immediately, and can send `contextBlocks` containing the full article for contextual consistency.
- `/api/summarize-article`: summarizes saved articles for the homepage list.
- `/api/ask-sentence`: answers follow-up questions about a selected sentence.
- `/api/anki/*`: checks/creates Anki helpers, while browser-side AnkiConnect is still required for local note import.

DeepSeek-backed routes default to `deepseek-v4-pro` and send `thinking: { type: "disabled" }` in completion requests. `DEEPSEEK_MODEL` is the shared override, while `DEEPSEEK_TRANSLATION_MODEL` takes precedence for full-article translation. Structured word explanations can retry comma-separated `DEEPSEEK_FALLBACK_MODELS` on the primary provider and can use a secondary `DEEPSEEK_FALLBACK_BASE_URL` with optional fallback key/model; sentence questions also use the fallback model list. The word explanation route sends compact `w/s/p/n` JSON keys to reduce request tokens; the full-article translation route accepts target article blocks plus optional full-article context blocks and sends compact `[id,type,text]` tuples to DeepSeek while preserving id-aligned JSON output.

## Anki Templates

`lib/ankiTemplates.ts` defines the Context Reader cloze and basic note types. The import flow calls `ensureModel`, so existing note templates are updated before new notes are added. Cloze-card front prompts are generated locally in `lib/ankiData.ts` from the durable explanation's exact `contextMeaning`: only that word-or-phrase translation appears after the large gap, with no basic meaning, sentence translation, fallback, or added label. Card backs include Anki native TTS replay controls for US and UK pronunciation. The UK control requests `en_GB` without hard-coding voice names, allowing Anki to select an installed British English voice across operating systems.

The app does not generate or store `[sound:...]` media files for pronunciation. During import, `addVocabularyNote` tries to set the target deck config's `autoplay` option to `false` through AnkiConnect so the card back does not auto-play pronunciation and users click the replay controls instead. If an older AnkiConnect/Anki combination cannot save deck config, note import still proceeds and the user can turn off audio autoplay in Anki deck options.

## Public Recommendations

Public articles are stored in Supabase tables created by `docs/public-articles-supabase.sql`. The Admin intake surface treats browser-local saved articles, pasted text, and URL import as equal entry modes in one candidate editor. URL intake reuses `/api/import-url`, preserves meaningful inline images, and receives description plus cover candidates. `/api/admin/article-classification` uses DeepSeek when configured and local readability/topic rules as a fallback. It produces a Chinese summary, Chinese learner difficulty, CEFR reference, audience stages, interest topics, reading time, timeliness, and review notes. Those classification fields are displayed as system-owned output rather than editable admin choices.

Candidates reuse `public_articles` rows with `published=false`. Recommendation metadata is stored in `imported_article.recommendation`, including the required cover URL and attribution, so existing production tables do not need a destructive schema migration. Missing-cover candidates remain editable but cannot publish. `/api/admin/article-covers` uploads reviewed files to the public `public-article-covers` Supabase Storage bucket. The editor can only save a candidate; selected ready candidates can be published only from the candidate list after an optional read-only user-view preview. When a candidate matches an existing public source URL or pasted-article identity, publishing updates the public row and removes the draft instead of creating a duplicate. Existing explanation and full-translation caches still use `article_id + cache_key` rows in `public_explanations` and `public_article_translations`.

`lib/recommendationSources.ts` is the crawler source whitelist. `lib/recommendationCrawler.ts` reads RSS/Atom feeds through the pinned-DNS remote fetch helper, accepts only article hosts declared by each source, removes tracking parameters, deduplicates against both candidate and public rows, reuses `/api/import-url` for article extraction, and reuses the same classification service as manual intake. A run stops after two successful additions or its bounded execution budget. Difficulty filtering happens after classification. Missing-cover results remain candidates and cannot publish. Feed failures and blocked article pages are isolated as per-item or per-source skips so one source cannot abort the whole run.

`POST /api/admin/article-crawler` performs an authenticated manual run with topic, optional difficulty, and target inventory. `GET /api/admin/article-crawler` returns source and schedule status. `GET /api/cron/recommendations` is called once daily by Vercel Cron, rotates across the six topics, and targets six candidate-or-public articles per topic. It requires `Authorization: Bearer $CRON_SECRET` and fails closed when the secret is absent. Cron delivery can be duplicated, so source-URL deduplication is part of the job's idempotency boundary; crawler output always enters review rather than publication.

The three public-content tables enable RLS and revoke all direct table privileges from `anon`, `authenticated`, and `PUBLIC`. Only the server-side service-role path reads or writes them; applying the SQL to the real Supabase project is part of deployment, not merely a documentation step.

When the public-recommendation scene becomes visible, `HomeClient` prefetches the visible article details and deduplicates hover, focus, and click requests in memory. The public-article server read fetches explanation and translation-cache rows in parallel after locating the article. On open, `HomeClient` writes returned `articleTranslations` into the browser's local translation cache before entering the reader. The reader then opens the full-article translation sidebar from cache instead of regenerating when the cached block hash matches the article text.

The admin UI follows one sequence: choose a browser-local, pasted, or URL source; accept automatic classification; review the cover and summary; save a candidate; preview the user-facing reading layout; then publish selected candidates. Topic-based discovery is a secondary collapsed intake source that reports inventory movement and skipped-item reasons but never publishes. The public list owns delete and per-row cache-refresh maintenance, so there is no duplicate local-article publishing selector. Candidate preview is intentionally read-only until the developer account and admin entry are unified. Visitors can read public articles without logging in.

Feedback submitted by `FeedbackPanel` is stored as bounded private JSON under month folders in the `context-reader-feedback` Supabase Storage bucket. `/api/admin/feedback` lists at most the latest 300 objects in bounded batches, treats older objects without status as new, updates `new`/`resolved` status by replacing the same private object, and deletes only validated feedback paths. The Admin view deliberately omits user-agent and Storage paths from its visible content.

## Offline Behavior

The production app registers `public/sw.js` as a service worker. After the site has been opened online once, the cached app shell can reopen offline. Public article API responses use network-first caching, expire after seven days, and are capped at fifty entries, so public articles that have already been loaded can reopen offline without growing an unbounded or indefinitely stale cache. Local browser data can reopen previously cached explanations and full translations. New AI explanations, new full-article translations, URL import, image OCR, and article summaries still require network access.

## OCR Provider Framework

`lib/visionOcr.ts` provides both plain-text extraction and layout-word detection. It supports `OCR_PROVIDER=zhipu` with `ZHIPU_API_KEY`, `ZHIPU_BASE_URL`, and `ZHIPU_OCR_MODEL`, and `OCR_PROVIDER=openai` with `OPENAI_API_KEY` and `OPENAI_OCR_MODEL`. If `OCR_PROVIDER` is omitted, the provider layer prefers Zhipu when `ZHIPU_API_KEY` exists, otherwise OpenAI when `OPENAI_API_KEY` exists.

The homepage and OCR routes are enabled. Enabling automatic OCR for URL-imported article images is a separate product decision controlled by `IMAGE_OCR_ENABLED` in `components/ReaderView.tsx`; it must account for request volume, provider reliability, persisted block metadata, and public/admin replay before that gate changes.

## Design

The reading workspace keeps the quiet utility treatment: no global black nav, compact rounded white surfaces, a system font stack, and Action Blue `#0066cc` for core reader controls. The homepage uses a light continuous depth scene, editorial serif sentences, blue reading actions, restrained coral/blue connective lines, and purposeful loading and scroll transitions. These effects teach actual reading gestures; they must not appear inside the article reader or obscure the first-screen entry.
