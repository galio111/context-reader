# Context Reader Architecture

## Overview

Context Reader is a Next.js app with a client-side reading workspace and server-side AI/helper routes. The shipped Home V2 supports two article entry modes:

- Plain text paste: stores and renders text only.
- URL import: server extracts public HTML into structured blocks, then the reader renders headings, paragraphs, nested ordered/unordered lists, quotes, captions, tables, images, and inline upper/lower annotations.

Legacy image-import and OCR code remains available but has no root-homepage entry. Automatic OCR for images embedded in URL imports also remains disabled in the reader.

Primary production runs at `https://context-reader.com` on a Tencent Lighthouse instance. Caddy terminates HTTPS and proxies the unchanged Next.js application to a private Docker network containing PostgreSQL 17, GoTrue Auth, PostgREST, Storage API, and the internal Supabase-compatible gateway. The browser still receives no database or service-role key. The former Vercel deployment and managed Supabase project are frozen rollback evidence only; production never reads or writes them.

## Reading Flow

`app/page.tsx` server-loads public recommendations and passes them to `HomeClient`, which owns the active article and home/reader state. `app/home-v2/page.tsx` permanently redirects legacy links to `/` while preserving their query string. Plain text articles pass only `article` into `ReaderView`. URL imports also pass `importedArticle`, which contains rich `blocks`. A text block's plain `text` remains the source for lookup, summaries, copying, and saved article identity; optional `inline` segments preserve visual annotations such as original `sup` and `sub` text. Table blocks keep caption, row/cell text, header scope and bounded row/column spans. They remain inside the article measure on desktop, use a local horizontal scroller on narrow screens, and tokenize each cell so contextual lookup remains available without turning the entire page into a horizontal scroller. Ordered list start values and bounded nesting levels also survive import. Before a rich article becomes visible, `ReaderView` preloads and decodes at most its first three image-block sources in parallel, then reveals text and images together. The gate settles after about 1.4 seconds even when an image stalls, while later eager images continue loading against their stored dimensions and the existing source-alignment stabilizer. Cross-article vocabulary jumps wait for that gate before locating the target token, so the loading state cannot consume the jump and leave the reader at the article start. The gate uses a compact animated article skeleton with a reduced-motion fallback. Image blocks render as article media with a click-to-enlarge zoom viewer. The viewer uses wheel zoom anchored at the cursor position, blocks background scrolling, exposes a download action, and renders clickable overlays when `layoutWords` are stored.

The shared/legacy image-import path can call `/api/ocr-image` and `/api/ocr-image-layout` in parallel, use layout text as a fallback, store the uploaded image as a data URL, and retain detected `layoutWords` or `layoutError`. It is not exposed by the shipped root homepage. `ReaderView` keeps `IMAGE_OCR_ENABLED = false`, so it does not automatically OCR arbitrary images embedded in URL imports; existing `ocrText` remains backward-compatible data. `ReaderView` tokenizes text blocks so word selection, phrase dragging, cached explanations, vocabulary saving, CSV export, and Anki import work across plain and URL-imported articles.

Saved articles live in browser `localStorage` through `lib/articles.ts`. `SavedArticle.importedArticle` is optional for backward compatibility. When present, reopening a saved URL import restores the original structured layout, images, supported inline annotations, and any OCR text already attached to image blocks instead of falling back to plain text. New URL imports contain only first-party Storage URLs for remote image blocks. A historical browser-only article that still contains an external image enters Reader immediately and starts the authenticated `/api/article-images/localize` repair in the background; it never blocks article opening on a media migration. Every successful replacement is persisted locally and normal protocol-2 sync carries the updated payload to the account without clearing unrelated data. The pinned-DNS IPv4 guard blocks exact private, link-local, carrier, documentation and reserved ranges rather than broad public `/16` ranges; for example, the public WordPress VIP address `192.0.66.108` used by `science.nasa.gov` must remain reachable while `192.0.0.0/24` and `192.0.2.0/24` remain blocked.

`components/PronunciationButtons.tsx` always renders compact US/UK playback controls for explanations and vocabulary entries. `/api/pronunciation` reads or generates a provider MP3 and returns identical audio across browsers and devices. Successful client requests are reused in memory and generated files are content-addressed in the private `context-reader-pronunciation` Supabase Storage bucket. Active explanation, dictionary-result, Anki-preview, and Menu-detail surfaces request both accents in the background before the user clicks; playback resumes the browser audio context during the click and decodes the returned MP3 without relying on browser text-to-speech. A still-pending first generation is visibly labeled `准备中`. Cloud failure remains explicit and never silently switches to `SpeechSynthesis`, because that would make Chrome, Edge, and mobile devices sound different.

## Article Editing

`ReaderView` edits article text in place rather than replacing the article with a textarea or a separate block editor. Read and edit states share `textBlockClassName`, so entering edit mode must preserve the same font size, line height, tracking, width, wrapping, and paragraph margins. Word lookup is disabled while editing. The toolbar provides global article undo and redo for the current reading session, not browser-native `execCommand` undo/redo. The history starts when the reader opens and remains available across edit mode and saved states until the user returns to the homepage. Imported article images are displayed but are not editable or uploadable; edit mode can remove an image block through the image's top-right delete button.

Plain text uses one `contentEditable` root containing the rendered paragraph elements. Imported articles also edit text blocks directly in the reading canvas while keeping image blocks read-only. Input events update the session history but still do not control the editable DOM on every keystroke, because rerendering controlled editable content moves the caret to the start. Save reads direct child text through `textContent`, normalizes non-breaking spaces, preserves explicit blank paragraphs as durable content, and serializes paragraphs deterministically. A no-op save exits without rewriting the article.

Imported articles edit each text block in place and rebuild `ImportedArticle` only when text actually changes. Empty accidental list-item blocks are removed on save, durable blank non-list paragraphs are preserved, image and table blocks are read-only and retained unless explicitly deleted, and an edited inline block drops its original `inline` segments when the new plain text no longer matches them. `lib/articles.ts::saveEditedArticle` preserves the saved article id, summary, creation time, and Anki-related local data while updating the body, title, rich blocks, and `updatedAt`.

Opening a saved article calls `touchSavedArticle`, refreshes `updatedAt` and the dedicated optional `lastOpenedAt`, and moves it to the front of the local array. `lib/savedArticleMerge.ts` collapses identical bodies and legacy `-local-recovered-*` lineages into one canonical original article, keeps the richest durable payload, carries forward the newest open/update time, and emits tombstones for every discarded id. The homepage saved-article menu therefore renders each logical article once and sorts by `lastOpenedAt`, falling back to legacy `updatedAt` and `createdAt` values. The reading-view vocabulary drawer can resolve a source sentence against all saved articles. Vocabulary created inside a public recommendation also stores an optional durable `sourceArticle` reference with the public id and title, so a source jump can load the recommendation directly without a local save; legacy entries without that field lazily scan the server-rendered public inventory, then persist the discovered reference through normal vocabulary sync. When the match is outside the current article, `HomeClient` starts a fresh reader session with that article before highlighting the source, preventing stale article state from consuming the jump request. Long articles keep every text block in the document from the first frame, but only the opening blocks and blocks near a settled viewport are tokenized into interactive word nodes; below-fold blocks remain complete plain text with identical typography. While wheel or scrollbar movement is active, `IntersectionObserver` keeps only the final nearby candidates and does not promote blocks crossed in transit. After the document has been still for a short interval, those candidates are promoted in a React transition, so lookup becomes available without constructing thousands of word nodes during the scroll gesture. Reader blocks must use their real layout height rather than `content-visibility` intrinsic-size estimates, because changing estimated block heights while the scrollbar thumb is being dragged makes the document length itself unstable. Reading-progress capture follows the same settled-scroll boundary and resolves the current block through the element at the reading line, with a logarithmic geometry fallback, instead of scanning every prior block on every animation frame. A source jump bypasses progressive tokenization so its target tokens exist immediately. Source jumps carry a monotonically increasing request id, wait for the article media gate and every vocabulary/menu scroll lock to release, then retry until the target tokens exist; the generic reader-entry scroll reset must not run for a pending source jump. The matched block is centered instantly without animating across the document. Recommendation opening starts its data request before the cover animation finishes and primes the leading inline image through a shared bounded cache. Reader entry gates only on that first image for at most 1.6 seconds; it is eager/high priority, while later images are lazy/low priority. Imported image blocks persist source width and height when available so the browser reserves their aspect ratio before download; legacy blocks without dimensions receive a 4:3 fallback ratio until their natural dimensions arrive, preventing a lazy image from beginning at zero height. During a source jump, preceding legacy images without dimensions are promoted from lazy loading and their load/error layout events keep the target sentence centered for a short stabilization window. Location highlighting is presentation-only: the source sentence receives a quiet highlight and the selected vocabulary word or phrase receives a stronger amber underline treatment without focus changes, article edits, history entries, or cache-key changes.

## Translation Flow

Sentence context uses punctuation-aware boundary scanning so periods inside common abbreviations, names and initials, numbers, numbered labels, domains, email addresses, and similar dot-joined tokens do not split lookup context prematurely.

Word and phrase lookups send only the selected text plus current, previous, and next sentence context to `/api/explain-word` and, on cache misses, `/api/explain-word-stream` in parallel. The stream uses fixed labels for lemma, current-form phonetic, part of speech, difficulty, meanings, sentence translation, usage, collocations, and examples. `ExplanationPanel` parses those labels into one progressive visual tree. The streaming route emits an internal completion boundary immediately after the last display field and before usage bookkeeping closes the response. At that boundary, `lib/explanationDisplay.ts` validates the complete visible result, records `phoneticFor` as the exact selected word or phrase, derives the local Anki fallback fields, caches it by `word + sentence`, and immediately enables vocabulary, copy, and sentence-question actions. Structured and standalone dictionary responses follow the same ownership rule: IPA belongs to the exact selected/query form, never implicitly to `lemma`. Display, CSV, vocabulary and Anki exports use `currentFormPhonetic`; legacy entries without an ownership marker may reuse IPA only when `word` and `lemma` are the same normalized form. When they differ, the ambiguous old IPA is hidden until regeneration rather than being relabelled. The interface renders `原型` and `当前词音标` on separate rows, while pronunciation controls always receive the visible current word. Those actions never wait for usage bookkeeping or the parallel structured request. When the structured response arrives, its hidden/durable fields such as Anki metadata merge with the stream's visible authority without replacing what the user already saw. Cache replay formats the merged fields back into the same fixed-label text, preserving content, order, spacing, and wrapping. `scrollbar-gutter: stable` prevents action controls from triggering width reflow. Collocations include parenthesized Chinese translations. Repeated taps do not restart an in-flight lookup; the circular regenerate control forces a new result and, when the same `word + sourceSentence` exists in vocabulary, replaces its generated fields while preserving id, creation time, and Anki import status.

Full-article translation uses `/api/translate-article` and appears in the reading view's right sidebar. Users start a new translation from inside that sidebar; there is no top-bar full-translation button and merely entering the sidebar does not start new AI work. The client derives translation blocks through `lib/articleTranslationBlocks.ts`, requests one text block at a time, appends each completed translation to the sidebar, and immediately persists both the current merged partial result and the completed per-block entry in `localStorage`. Those cache objects enter account sync independently of saved-article objects, so signed-in users can reopen the same recommendation on another device without first saving the article. Cache reads merge the newest exact whole-article entries over any still-available per-block entries, allowing older blocks to repair a partial whole-article result left by the former destructive regenerate flow. Partial results therefore survive route changes, refreshes, browser restarts, and account sync; returning to an already-started incomplete article resumes only missing blocks. Public/admin preloads seed only missing whole-article cache keys, and preloaded explanations likewise seed only missing explanation keys, preserving the member's cloud-restored or regenerated values. After article editing, unchanged block keys reuse their cached translations while changed blocks are marked stale; “更新已修改部分” requests only those changed blocks. Keep the batch size at one block unless there is a deliberate UX tradeoff, because the first translated paragraph should appear as soon as it is ready and later paragraphs should continue appearing after it. The request-security translation bucket is sized for a normal multi-paragraph one-block sequence; if shared-IP pressure still reaches it, middleware returns `site_rate_limit` plus `Retry-After`, and the client remains in a reasoned waiting state instead of surfacing a terminal red error. Each translation request includes the full current article as `contextBlocks`, so one-block requests still give the model article-level context. Switching back to word explanations must not abort the in-flight translation. Provider rate limits, overloads, timeouts, network interruptions, and the local concurrency cap use bounded queueing plus cancellable exponential backoff; quota, provider balance, and configuration failures remain explicit non-retryable errors. The circular regenerate button bypasses whole-article and per-block caches when deciding what AI work to request, but does not delete the prior durable result first: every previously completed block remains visible and cached until its fresh replacement succeeds, then replacements are merged and persisted one by one. `lib/articleTranslationJobs.ts` estimates remaining time from freshly completed target blocks rather than counting retained fallback translations as regenerated work.

## Homepage

Reader night mode is a shared surface system, not a body-background inversion. `app/globals.css` defines the reader canvas, panel, raised/soft surface, primary text, muted text, accent and boundary ramp; the same ramp applies to the article, explanation and translation sidebars, vocabulary drawer, account/guide Menu previews, inputs, tables, notices and image-viewer controls. `WordToken` exposes explicit selected, highlighted and source-target states so hover, selection and jump highlighting keep paired foreground/background colors instead of inheriting the daytime pale fill. `PronunciationButtons` and `ArticleTranslationPanel` likewise expose semantic control and state classes for default, hover, focus, playing, regenerate, retry, progress, warning and disabled states. Reader panel tabs expose `data-active`, so their night colors no longer depend on matching Tailwind class strings. CSS-module surfaces that own their own palette, including `HomeOptionMenu`, `ReaderToolbar`, `BookDictionary`, `GuidePageContent`, `HomeRedesign` and vocabulary learning details, define night rules after their daytime declarations so the cascade cannot restore low-contrast daytime text or cards. The guide keeps one paired palette in both its standalone route and embedded Menu preview; its nested Anki assistant has explicit dark step surfaces. Desktop embedded dictionaries and mobile compact dictionaries share the same result, example, disabled and empty-state ramp. Every future UI change must ship day and night colors together and verify default plus interaction states at practical WCAG AA: 4.5:1 for normal text and placeholders, 3:1 for large text and non-text controls.

`ArticleInput` and `ImmersiveHome` retain legacy/shared entry behavior, but neither is a new design baseline. `/` is the canonical homepage; reusable article import, saved-article, vocabulary, account and `ReaderView` contracts remain shared beneath its presentation layer.

`app/page.tsx` server-loads public article summaries plus the independent homepage-curation setting and renders `HomeClient`; legacy `/home-v2` requests redirect to the root. `HomeRedesign` is the current real presentation layer while `HomeClient` owns the durable boundary: active article state, URL/paste import, recommendation detail fetch and prefetch, cache preload, saved articles, vocabulary-source jumps, reader transition and `ReaderView`. Publishing and homepage placement remain separate; an empty curation falls back to the legacy public order during migration.

The current implementation still renders `BookHome`, whose desktop controller combines a closed cover, Ballpit scene, chapter spreads, scroll-driven `CurvedPageTurn` snapshots, idle settle and nested wheel-boundary handling. Those mechanisms explain the code in the audited worktree, but the accepted product direction supersedes them: retain the cover and Ballpit as a brand/IP surface, remove all cover/inner page turns and scroll-driven turning, and let a cover or primary-action click reveal real recommendations and reading entry quickly. The old page-flip geometry, timing constants and wheel arbitration are therefore migration/removal concerns rather than protected architecture.

Do not build a parallel `/home-lab` or a static mock. Iterate on the real root homepage in a branch, with server-rendered articles and `HomeClient` callbacks connected in the first reviewable slice. Once the replacement flow is accepted and covers all required functions, remove unused `CurvedPageTurn` code, page-turn CSS, listeners, dependencies and obsolete regression rules together instead of preserving two homepage engines.

UI verification has three independent layers: technical correctness, visual fidelity to the user-confirmed reference and repeated-use product experience. Browser keyframes or a short comparison recording are required for a positive visual-fidelity claim; build/HTTP/state-machine evidence alone establishes only technical correctness. See `docs/home-v2-implementation-contract.md` for the current/target contract and validation workflow.

`BookDictionary` consumes `/api/dictionary-stream` as newline-delimited structured events. Each complete event mounts the matching final UI block in order, and the accumulated event model becomes the saved and cached `DictionaryResult` without a completion-time layout swap. The route accepts a short Chinese query for Chinese-to-English or the existing English word/eight-word phrase for English-to-Chinese. English keeps the existing deep-dictionary hierarchy and reader-panel presentation, including its headword, pronunciation, senses, applicable past/past-participle/present-participle forms, concrete usage guidance, three or more useful collocations, reasonable word family and synonyms, mistakes, and memory guidance; streaming output must not silently reduce this to the compact Chinese-to-English shape. The head event includes `phoneticFor`; for English input it must equal the exact query, so a lookup for `tilted` can show `原型：tilt` separately while the IPA and both audio controls remain explicitly attached to `tilted`. The standalone session and durable cache schema versions changed with this invariant, preventing an older lemma-owned IPA from replaying as current-form data. Chinese remains the visible headword; candidates are grouped by part of speech before every independently pronounceable English expression shows its own IPA, register, usage note, and bilingual example, followed by one concise comparison section and optional genuine mistake warnings. The provider returns one candidate when one is sufficient and multiple candidates when common contexts require different choices; Chinese-to-English does not render English-to-Chinese collocations, word family, synonym grids, or memory tips. The homepage compact dictionary and the article reader's narrow dictionary panel share data and actions but not a scaled copy of the same Chinese-to-English layout. Only the reader panel's Chinese-to-English result uses the container-specific hierarchy: each expression, metadata, IPA, equal-width pronunciation controls, usage note, and example occupy stable vertical rows; numbered meanings keep a narrow fixed gutter. Shared history keeps four equal-width recent-query pills on one line at standard sidebar width and five in a wider container, truncating long labels with an ellipsis before the full-width expandable list. Expanded history rows expose a separate accessible delete action that removes only that lookup and syncs its deletion. English head events still classify `valid`, `inflection`, or `misspelled`, and the spelling-correction boundary is unchanged. Both directions reuse the same DeepSeek defaults, concurrency/usage accounting, history, durable cache, account sync, and offline replay; the circular regenerate action deliberately bypasses lookup cache and overwrites it only after a complete new result arrives. Saving English-to-Chinese carries verb forms into study notes. Saving Chinese-to-English uses the first English candidate only as the vocabulary and TTS identity while preserving all part-of-speech groups and the Chinese cue in `basic_cn_to_en_dictionary`; its Anki front is Chinese and its back contains the candidate expressions, pronunciation, examples, comparison, and useful warnings. Article-derived cloze and fallback CN-to-EN cards are unchanged.

Public recommended articles are fetched in the server `app/page.tsx` and passed into the client homepage as `initialPublicArticles`. Do not move this list back to a client-only `useEffect` fetch; otherwise the recommendation spread first renders without them and visibly fills them in later. Saved articles belong to the shared Menu rather than the recommendation spread.

The reading view uses the same vocabulary data but keeps the notebook as a right-side drawer so it does not cover the article workspace. Both notebook placements lock the underlying page at its current scroll position while preserving an explicitly sized, `min-height: 0` internal scroller for the notebook. The homepage's global wheel/touch teaching locks and desktop scene snapping must ignore events from marked local-scroll surfaces, and notebook overscroll stays contained instead of reaching the page. Vocabulary is always sorted by `createdAt` descending after normalization, deduplication, and cloud merge, so account login cannot inherit the sync table's object-key order. Entries use TanStack Virtual with stable entry keys, transform positioning, small bounded overscan, content-aware unmeasured-height estimates, animation-frame ResizeObserver batching, and live element measurement. Scrollbar dragging does not trigger compensating scroll-offset writes as new rows are measured. Only rows near the viewport mount, hidden homepage animation frames and CSS animations pause while the notebook is open, and the overlay avoids a full-screen backdrop filter. Do not reintroduce fixed oversized rows or React state updates on every scroll event; short cards should stay compact and long cards should remain fully visible.

Shared tool panels should not preserve stale interaction traces across open/close cycles. `VocabularyPanel` clears its search, preview, and expanded-detail state and scrolls its list to the top when opened or when the filtered list changes. Vocabulary rows always show IPA when available plus the original core fields; usage notes, collocations, and bilingual examples are progressively disclosed by the per-entry `显示全文` control. Rows continue to use measured content heights before and after expansion. `lib/vocabularySearch.ts` builds a sorted normalized-word index once per ordered collection and resolves prefix searches with binary bounds, so query cost scales with matches rather than total stored vocabulary. Browser TTS voice discovery and warmup are shared across memoized pronunciation controls rather than repeated when virtual rows mount. The Home Menu vocabulary preview uses fixed compact virtual rows without per-row resize observers, disables their pointer targets while the list is actively scrolling, and therefore does not replace the hover detail for every row passing beneath a stationary pointer. Parent views clear temporary vocabulary errors and Anki status when the drawer/dialog closes.

## Mobile Reader

The mobile reader keeps the article as the primary single-column surface and puts a fixed tap-only tool dock above the safe area. Explanation, full-article translation, standalone lookup, vocabulary, and lower-frequency article actions share a draggable near-full-screen sheet; switching tools changes the sheet body without moving the reading position. Opening full-article translation must not start the job automatically. Anki import controls are absent on mobile but remain available on desktop. The sheet owns its local scroll and overscroll containment, and only its compact handle/collapse control stays fixed while content scrolls. Image zoom, fit, download, and close actions appear in a bottom image-viewer toolbar after an image is tapped. Vocabulary CSV export and destructive clearing stay inside a secondary action disclosure.

Touch word selection separates reading scroll from lookup gestures. Vertical movement is treated as article scrolling and should not highlight or query a word. A tap explains one word. Horizontal movement across words or long-press selection can select a short phrase, capped at eight words.

Each new explanation resets the bottom sheet to its default half-height and scrolls the explanation content to the top. Collapsing the explanation panel should preserve the article reading position, but temporary panel state should not leak into the next lookup.

## Account, usage, and sync

In mainland production, the server-side `SUPABASE_*` names are compatibility variables for the self-hosted adapters and always resolve to the private `supabase-api` gateway. Supabase Cloud is not an active data path. The mainland image refuses to start when the runtime mode is missing or `SUPABASE_URL` is external, while `/api/connectivity` exposes only the safe `mainland_internal` marker for release acceptance.

Account sync transport uses byte-bounded response pages. A protocol-2 bootstrap captures one latest-server cursor, transfers active payloads and a lightweight tombstone index through that fixed snapshot, and persists an opaque keyset cursor plus version/hash/deletion manifest. Every later pull reads only rows newer than `(updated_at, kind, object_key)`; it does not scan the complete account history. The `preferences/homepage-recommendation-preferences` object carries the account-scoped reading level and interests; guest-scoped browser preferences never silently overwrite an existing cloud account preference during login. Automatic learning-data sync remains active on `/admin` only for the developer account so vocabulary and locally saved articles created inside the real ReaderView are durable; password-only Admin sessions have no account sync. Normal pages serialize writes both within one tab and across tabs with the Web Locks API.

`AccountProvider` loads `/api/auth/session`, opens the phone/password form only for restricted actions, schedules cloud sync about 800 ms after durable local changes, pulls remote changes about every 15 seconds while visible and immediately on focus/visibility return, and requires a successful final sync before explicit logout clears browser data. Phone registration collects a nickname, maps the unverified mainland-China phone identifier to a reserved server-only Auth email, and stores the six-digit numeric password through Supabase's password hashing. Legacy email-link adoption remains compatible but is hidden from the current UI. The session includes the active entitlement source and dates; expired grants resolve to Free. `lib/accountSyncClient.ts` stores each article, vocabulary entry and explanation/translation cache item as an independent versioned object; cache durability does not depend on saving the article. Supabase compare-and-swap prevents stale devices from overwriting newer versions; client writes are single-flight, unique by kind plus object key, and retry after refreshing incremental server changes. The client compares normalized JSON payloads with stable key ordering and skips unchanged objects. Article conflicts resolve to one canonical article and discarded duplicate ids become tombstones; article sync must never create a visible recovery copy. The sync API also converts any legacy `-local-recovered-*` article write into a tombstone so an older open tab cannot resurrect deleted copies. After a cloud merge, `HomeClient` refreshes its saved-article state from durable storage immediately instead of showing a stale pre-sync count until reload. Vocabulary versions are normalized, merged and deduplicated by word plus source sentence while preserving optional public-article source metadata; redundant recovery ids become tombstones, while a genuinely ambiguous same-id/different-identity local value is preserved in a separate local recovery store and never counted as a notebook entry. Article and vocabulary deletions are persisted as tombstones so another device cannot silently restore them. Tombstone compaction is a future backend maintenance operation and must require a retention plus client-acknowledgement design before deletion.

For workstation-only development, `next dev` accepts only the loopback hosts `localhost`, `127.0.0.1`, and `[::1]` for local identity shortcuts. When ignored local environment configuration supplies a valid `LOCAL_DEVELOPER_USER_ID` alongside usable Supabase credentials, the request is represented as that exact Auth UUID and then passes through the normal profile, entitlement, usage, sync, and Admin checks. The browser preserves existing local content during the first transition to that UUID before normal versioned cloud merge. This does not infer developer access from a nickname: Admin still requires Supabase to report an active profile and active `admin` entitlement for the exact UUID. With no usable Supabase credentials, the loopback path instead uses a browser-local learning identity, disables cloud sync and remote export, bypasses cloud quota bookkeeping for local AI calls, and never grants Admin. Both shortcuts are disabled for production builds, `next start`, and non-loopback hosts, so neither is a deployed authorization path.

Saving an article commits the local article object and schedules account sync before requesting its generated Chinese list summary. Summary or provider failures therefore leave the article saved and retryable instead of rolling back the durable article record.

All cost-bearing routes use `lib/usageGate.ts`. Structured and streaming word lookup requests share `x-context-action-id`, so the quota action is idempotent while `usage_executions` stores both real upstream calls. Registered-user failures are refunded and cache hits are free; guest cached lookups call `/api/usage/cache-lookup`. Full translation, summaries, sentence questions and OCR require login. `/account/usage` is the user view; the unified `/admin` console manages public recommendations, users, ordinary-user limits, invitation codes, provider cost summaries, and feedback. Admin creates a random one-time code, stores only its SHA-256 hash and hint, and sees the plaintext only in the creation response. `redeem_invitation_code` locks the matching row, rejects revoked/expired/redeemed codes and active paid/invite entitlements, then atomically marks redemption and writes the fixed-duration entitlement. Admin quota rows are grouped by Chinese product meaning, batch-save the fixed metric/window pairs for each ordinary plan, and intentionally hide the developer allowance plus unconnected price settings.

The browser never receives a Supabase key. Without account infrastructure, reading and a browser-enforced ten-lookup fallback remain available, while login and authenticated high-cost features remain disabled.

## API Routes

`middleware.ts` and `lib/requestSecurity.ts` form the common request gate. They apply trusted reverse-proxy client/origin extraction, route-specific fixed-window limits, daily costly-operation limits, `413` early rejection, same-origin admin checks, request ids, and private admin cache headers. `lib/limitedBody.ts` also counts actual streamed bytes before JSON or multipart parsing, so missing or forged `Content-Length` cannot bypass route limits. `lib/costConcurrency.ts` caps simultaneous AI and OCR work per server instance and releases leases on completion, error, stream cancellation, or client disconnect where the upstream route exposes a signal.

All user-controlled outbound URL reads use `lib/safeRemoteFetch.ts`. It accepts only standard-port HTTP(S), rejects credentials and non-public/reserved IP ranges, resolves and pins the verified IP for the actual TCP/TLS connection, preserves the original Host/SNI, rechecks every redirect, and streams responses through hard byte caps. AnkiConnect accepts only local `127.0.0.1:8765` and has an eight-second timeout.

- `/api/public-articles`: lists public recommended articles for clients and service-worker caching. The homepage does not depend on a client-side call for first paint.
- `/api/public-articles/[id]`: reads one public article plus its preloaded word explanations and full-article translation caches.
- `/api/auth/*`: registers/signs in phone + numeric-password accounts, retains legacy email OTP and hosted-session adoption, reads/refreshes the current account session, and logs out through server-managed cookies.
- `/api/account/sync`: reads and compare-and-swap merges versioned account objects; `/api/account/export` returns the member's profile, synced objects, and usage-action history.
- `/api/usage/cache-lookup`: completes an idempotent cached guest action; the current `finalize_usage` contract refunds its reserved unit, so cache hits do not consume either guest lookup pool.
- `/api/account/profile`: updates the authenticated account's nickname and optional reading profile with bounded, allow-listed fields. The current UI edits English level and interests and can clear demographic fields.
- `/api/account/invitation-code`: redeems one hashed, single-use invitation code for the current signed-in account; `/api/admin/invitation-codes` creates, lists and revokes codes under server-authorized Admin.
- `/api/admin/homepage-curation`: server-authorized Admin read/write surface for the independent homepage showcase order. Publication status and homepage placement remain separate.
- `/api/admin/*`: handles public article listing/publishing/deletion, account/quota administration, private feedback listing/status/deletion, and detailed error-report review. `lib/adminAuth.ts` accepts a server-verified user whose entitlement is `admin` or the signed legacy password-admin cookie; client-side menu visibility is never the authorization boundary. Writes still require same-origin requests.
- `/api/import-url`: fetches bounded public HTML through the pinned-DNS safe path and parses it in a server-side DOM without executing page scripts. The extractor removes explicit hidden/inert/ARIA-hidden content plus high-confidence navigation, advertising, sponsored, newsletter, sharing, comments and related-card subtrees. It compares Mozilla Readability output with site-semantic `articleBody`/article/main/content candidates, preferring the narrower readable result unless a clean structural candidate contains materially more substantive text or preserves tables/images Readability lost. This conservative comparison protects completeness instead of treating any single heuristic as authority. It then applies the shared block-level trailing boundary, including explicit `-end-` markers after sufficient article content. The returned blocks preserve headings, paragraphs, ordered/unordered list level and ordinal, quotes, figure captions, meaningful inline images, `sup`/`sub`, and bounded structured tables with header scope and row/column spans. Before returning the article, the server fetches those selected image subresources through the same pinned-DNS boundary, converts them to bounded content-addressed WebP files and replaces every remote block URL with first-party Storage. Direct retrieval is preferred; when mainland egress or anti-hotlink behavior blocks a public source, `images.weserv.nl` may be used only as a server-side ingestion transport after the original URL passes the private-network check. The proxy response still passes byte, pixel and Sharp decoding limits, and neither proxy nor source URLs are retained in the successful article. If any selected image cannot be stored, the import fails before the guest allowance is charged instead of returning a durable broken hotlink. Link-dense repeated cards and linked teaser images are omitted, while ordinary inline citations remain. A standalone advertisement label is retained only when the article is substantively about advertising. Fully dynamic pages, login walls and strong anti-bot challenges can still fail because the importer deliberately does not run arbitrary remote JavaScript.
- `/api/ocr-image`: extracts text from one uploaded image up to 8MB.
- `/api/ocr-image-layout`: detects word boxes for multipart uploads, data URLs, or remote image URLs and returns percentage coordinates plus line context.
- `/api/ocr-image-url`: extracts text from a remote image URL. The route is enabled, but the URL-import reader does not call it automatically while its OCR gate is off.
- `/api/article-images/localize`: authenticated, rate-limited lazy repair for external image URLs inside a historical browser-local saved article.
- `/api/download-image`: fetches and validates a remote image up to 20MB and returns it as a short-lived private attachment.
- `/api/explain-word`: sends only selected word/phrase and sentence context to DeepSeek.
- `/api/explain-word-stream`: sends the same selected context to DeepSeek and streams fixed-label Chinese text whose completed visible fields are merged into the durable explanation.
- `/api/dictionary`: accepts a Chinese word/short phrase, one English word, or an English phrase of up to eight words, consumes one `lookup_generation` unit, and returns a detailed bidirectional context-free dictionary result. It uses the same DeepSeek defaults, request-size limits, execution ledger, estimated-cost recording, and AI concurrency guard as the other generated lookup paths.
- `/api/translate-article`: translates sanitized article text blocks to Chinese for the full-article translation sidebar. The client requests one text block at a time with `contextBlocks` containing the full article, while the route briefly queues behind the in-process cost cap, passes a privacy-safe hashed `user_id` for provider scheduling isolation, and returns structured retry codes that distinguish temporary provider pressure from quota, balance, and configuration failures.
- `/api/summarize-article`: summarizes saved articles for the homepage list.
- `/api/ask-sentence`: answers follow-up questions about a selected sentence.
- `/api/pronunciation`: validates a bounded English word or short phrase, reads a private content-addressed MP3 cache, and calls Volcengine TTS only on a miss.
- `/api/anki/*`: checks/creates Anki helpers, while browser-side AnkiConnect is still required for local note import.

DeepSeek-backed routes default to `deepseek-v4-pro` and send `thinking: { type: "disabled" }` in completion requests. `DEEPSEEK_MODEL` is the shared override, while `DEEPSEEK_TRANSLATION_MODEL` takes precedence for full-article translation. Structured word explanations retry one transient transport failure, timeout, HTTP 429/5xx response, or JSON-mode empty response before failing; authentication and other non-retryable HTTP errors fail immediately. Admin diagnostics distinguish `provider_http_error`, `provider_timeout`, `provider_transport_error`, `provider_empty_content`, and genuine `provider_parse_error` reports. Structured word explanations can also retry comma-separated `DEEPSEEK_FALLBACK_MODELS` on the primary provider and can use a secondary `DEEPSEEK_FALLBACK_BASE_URL` with optional fallback key/model; sentence questions also use the fallback model list. The word explanation route sends compact `w/s/p/n` JSON keys to reduce request tokens; the full-article translation route accepts target article blocks plus optional full-article context blocks and sends compact `[id,type,text]` tuples to DeepSeek while preserving id-aligned JSON output.

## Anki Templates

`lib/ankiTemplates.ts` defines the Context Reader cloze and basic note types. The import flow calls `ensureModel`, so existing note templates and their `AudioUS`/`AudioUK` fields are updated before new notes are added. Article-derived entries use a context cloze whenever the selected target can be located in the source sentence and other English context remains after replacement; short words and function words such as prepositions, adverbs, conjunctions, pronouns, and auxiliaries are not downgraded merely because of their length or part of speech. The basic CN-to-EN fallback is reserved for structural failures such as a missing source sentence, a target that cannot be located without rewriting the sentence, or a target that covers the entire sentence. Cloze-card front prompts are generated locally in `lib/ankiData.ts` from the durable explanation's exact `contextMeaning`: only that word-or-phrase translation appears after the large gap, with no basic meaning, sentence translation, fallback, or added label. Card backs prefer attached cloud-generated US/UK MP3 media and use native `en_US`/`en_GB` TTS only when the matching media field is empty. Standalone `basic_en_to_cn` notes keep an English-only front and render a complete Chinese study back. Standalone `basic_cn_to_en_dictionary` notes reverse only the recall direction: the front is the Chinese query and the back leads with the English expression while preserving the same IPA, pronunciation, examples, and structured learning details.

`addVocabularyNote` retries transient pronunciation failures, then passes both base64 MP3 attachments to AnkiConnect, which stores them as deterministic `[sound:...]` media references. The note is created only after both recordings are available, so every successful new import owns the same US and UK cloud audio as the website; a persistent pronunciation failure leaves Anki untouched and can be retried later. Existing legacy cards are not bulk-upgraded. Desktop Anki then synchronizes imported files through normal AnkiWeb media sync for AnkiMobile and AnkiDroid. The flow also tries to set the target deck config's `autoplay` option to `false`; if an older AnkiConnect/Anki combination cannot save it, note import still proceeds and the user can turn off autoplay in Anki deck options.

## Public Recommendations

Public articles are stored in the active PostgreSQL tables created by `docs/public-articles-supabase.sql`; the SQL and API names remain Supabase-compatible even on the mainland self-hosted backend. The Admin intake surface treats browser-local saved articles, pasted text, and URL import as equal entry modes in one candidate editor. URL intake reuses `/api/import-url`, preserves meaningful inline images, and receives description plus cover candidates. `/api/admin/article-classification` uses DeepSeek when configured and local readability/topic rules as a fallback. It produces a Chinese summary, Chinese learner difficulty, CEFR reference, audience stages, interest topics, reading time, timeliness, and review notes. Those classification fields are displayed as system-owned output rather than editable admin choices.

Candidates reuse `public_articles` rows with `published=false`. Recommendation metadata is stored in `imported_article.recommendation`, including the required cover URL and attribution, homepage category and optional rejection timestamp, so existing production tables do not need a destructive schema migration. Rejected rows are hidden from the active queue, remain restorable, and continue participating in crawler URL deduplication. `lib/articleContentSanitizer.ts` also trims recognized trailing website sections when old remote-URL candidates are mapped for Admin preview and immediately before publication; publishing persists the cleaned body and blocks, while plain pasted candidates are untouched. Missing-cover candidates remain editable but cannot publish. Candidate saving deliberately does not download large remote media. At publication, `lib/publicArticleCovers.ts` resolves supported CDN source wrappers, fetches the reviewed cover and every remote body image through `safeRemoteFetch`, rejects invalid or oversized bodies, uses Sharp to normalize them to bounded WebP files, and stores them under SHA-256 content-addressed keys in the active public `public-article-covers` Storage bucket. Publication fails closed if any body image cannot be localized, preventing a new public row from depending on visitor access to an external CDN. The same direct-first, server-side ingestion fallback used by ordinary URL imports applies to public media; `static.time.com` uses the fallback first because direct mainland access is known to time out. No public or saved article receives a proxy URL. `/api/admin/article-covers` uploads reviewed files and exposes an authorized maintenance action for selected or all legacy published covers and body images; `ops/mainland/repair-public-covers.py` invokes that action without printing credentials. `/api/admin/saved-article-images` and `ops/mainland/repair-saved-article-images.py` perform a compare-and-swap migration of active synced saved-article objects: they preserve article ids, timestamps and content, advance the server version, and change only successfully localized image sources so connected clients receive the repair through protocol 2. Public-card and Reader image failures render quiet source-labelled fallbacks instead of browser broken-image UI. Candidate and published rows mount the same `ReaderView` used by normal reading. Admin reading wraps it with a fixed 330 px, independently scrollable metadata inspector and passes that desktop viewport inset into ReaderView; the fixed explanation/translation/dictionary rail, including its mode buttons, is positioned from the remaining reader viewport rather than the full browser viewport. Its optional `onArticleEditCommit` waits for the Admin candidate/public API to persist body and structured-block edits before closing edit mode; failures remain visible in the existing Reader status area. Title, summary, classification, and cover stay in the metadata editor. When a candidate matches an existing public source URL or pasted-article identity, publishing updates the public row and removes the draft instead of creating a duplicate. Existing explanation and full-translation caches still use `article_id + cache_key` rows in `public_explanations` and `public_article_translations`.

`lib/recommendationSources.ts` is the crawler source whitelist. `lib/recommendationCrawler.ts` reads RSS/Atom feeds through the pinned-DNS remote fetch helper, accepts only article hosts declared by each source, removes tracking parameters, deduplicates against both candidate and public rows, and reuses `/api/import-url` for the same balanced-container and trailing-noise cleanup as manual URL intake before classification. A run stops at the configured one-to-six addition cap or its bounded execution budget. Difficulty filtering happens after classification. Missing-cover results remain candidates and cannot publish. Feed failures and blocked article pages are isolated as per-item or per-source skips so one source cannot abort the whole run.

`lib/recommendationAutomation.ts` stores the automation config and last-run state in the server-only `account_settings` rows `recommendation_automation_config` and `recommendation_automation_state`. `GET /api/admin/article-crawler` returns this state; `PATCH` updates the enabled flag, Asia/Shanghai run time, and one-to-six candidate cap; authenticated `POST` supports a configured run-now action and an SMTP test. An explicit manual topic/difficulty scan uses `ignoreInventoryTarget` with a one-to-six addition cap, so an already-large inventory does not turn the user's action into a no-op; the scheduled job retains its inventory target to avoid unnecessary recurring work. The mainland systemd timer wakes every five minutes, while `GET /api/cron/recommendations` decides whether the configured daily run is due, already completed, or disabled. A due run rotates across six topics, targets thirty candidate-or-public articles per topic, and sends a summary through `lib/siteNotificationEmail.ts` only after successful scheduled completion. It requires `Authorization: Bearer $CRON_SECRET` and fails closed when the secret is absent. Delivery can be duplicated, so the stored Shanghai date and source-URL deduplication are both idempotency boundaries; crawler output always enters review rather than publication. `vercel.json` retains the former schedule only for a deliberate rollback deployment.

The three public-content tables enable RLS and revoke all direct table privileges from `anon`, `authenticated`, and `PUBLIC`. Only the server-side service-role path reads or writes them; applying the SQL to the real Supabase project is part of deployment, not merely a documentation step.

When the public-recommendation scene becomes visible, `HomeClient` prefetches the visible article details and deduplicates hover, focus, and click requests in memory. The public-article server read fetches explanation and translation-cache rows in parallel after locating the article. On open, `HomeClient` writes returned `articleTranslations` only when the corresponding browser cache key is absent, so an account-synced member translation remains authoritative. The reader then opens the full-article translation sidebar from cache instead of regenerating when the cached block hash matches the article text.

The Admin daily editorial workbench is reading-first: the real Reader occupies the center, its right reading tools remain present, and the fixed left inspector keeps judgement, previous/next, category and difficulty available while summary, rationale and evidence collapse. Metadata changes debounce-save and are flushed before navigation, selection or rejection. Far-right candidate and published drawers support search, category and difficulty filters and open any row into the Reader; the candidate drawer also exposes restorable rejection history. One-step URL intake imports, classifies and saves before opening the new candidate. Active candidates sort time-sensitive items first and otherwise newest-first. Selecting publishes the article, prepends it to global `推荐`, inserts it into the automatically derived or manually corrected category, and optionally makes it that category's first item; rejection hides the candidate but preserves a deduplicating, undoable record. Topic-based discovery remains a secondary collapsed intake source and never publishes. The whole Admin subtree forces the stable light visual scheme independently of the developer account's reading theme. Visitors can read public articles without logging in.

Feedback submitted by `FeedbackPanel` or the Home Menu is stored as bounded private JSON under month folders in the `context-reader-feedback` Supabase Storage bucket. Multipart submissions may add at most three JPEG/PNG/WebP/GIF files of at most 5 MB each under validated private attachment paths. `/api/admin/feedback` lists at most the latest 300 JSON objects in bounded batches, serves validated attachments only after admin authorization, treats older objects without status as new, updates `new`/`resolved` status by replacing the same private object, and deletes the JSON object together with its validated attachments. The Admin view shows image previews but deliberately omits user-agent and Storage paths from its visible content.

`lib/clientErrorReporting.ts` is the user-facing error boundary for browser requests. It preserves explicit 4xx input/auth/quota explanations, distinguishes a confirmed offline browser from an otherwise unreachable site, and converts 5xx failures into a maintenance message with a traceable id. Unsupported standalone dictionary input is rejected before network work: mixed-language input, overlong Chinese queries, and whole sentences receive direction-specific guidance before any request. Network and user-input failures are not stored as product bugs.

`lib/serverErrorReporting.ts` and `lib/errorReportStore.ts` persist site, provider, configuration, and client-processing faults as deduplicated private JSON under `errors/YYYY-MM/` in the feedback bucket. Each record includes operation, endpoint, user-facing and technical messages, stack, status/code, safe metadata, browser/user identity when available, deployment version, occurrence count, resolution state, and email-delivery state. The record is written before SMTP/Resend delivery; repeated email for the same fingerprint is suppressed for fifteen minutes. `/api/error-reports` is bounded, same-origin, and rate-limited for client-only failures. Only `/api/admin/error-reports` can list, update, or delete records.

## Offline Behavior

The production app registers `public/sw.js` as a service worker. After the site has been opened online once, the cached app shell can reopen offline. Public article API responses use network-first caching, expire after seven days, and are capped at fifty entries, so public articles that have already been loaded can reopen offline without growing an unbounded or indefinitely stale cache.

`AccountProvider` separates server authentication from offline local access. Every successful authenticated session writes a minimal `context-reader:last-account-session:v1` snapshot containing only the user id, nickname, and verification time. A failed `/api/auth/session` request, an explicit browser `offline` event, or a server-side account-service `503` changes the client to offline mode, removes all server-authorized account state, and reopens local data only when that snapshot exists. The UI keeps an always-visible offline banner and the Menu labels the identity as offline. The snapshot must never restore plan, usage, Admin visibility, or authorization for any API route.

An offline remembered account can open, save, and edit browser-local articles, read and modify its local vocabulary, and replay cached explanations, standalone dictionary results, and full translations. Those local mutations continue to emit the existing account-data events and sync after the server session is verified again. New AI explanations, standalone dictionary generation, full-article translation, URL import, feedback submission, article summaries, cloud sync, and usage reads require network access and must show an offline-specific message instead of opening a login prompt.

## OCR Provider Framework

`lib/visionOcr.ts` provides both plain-text extraction and layout-word detection. It supports `OCR_PROVIDER=zhipu` with `ZHIPU_API_KEY`, `ZHIPU_BASE_URL`, and `ZHIPU_OCR_MODEL`, and `OCR_PROVIDER=openai` with `OPENAI_API_KEY` and `OPENAI_OCR_MODEL`. If `OCR_PROVIDER` is omitted, the provider layer prefers Zhipu when `ZHIPU_API_KEY` exists, otherwise OpenAI when `OPENAI_API_KEY` exists.

The OCR routes and provider code remain dormant for compatibility and possible future work. No current user-facing page exposes OCR: both `components/ArticleInput.tsx` and `components/ReaderView.tsx` keep `IMAGE_OCR_ENABLED = false`. Re-enabling either path is a separate product decision that must account for request volume, provider reliability, persisted block metadata, public/admin replay, and a complete user-facing copy review.

## Design

The reading workspace keeps the quiet utility treatment: no global black nav, compact readable surfaces, and restrained core controls. The homepage may use the accepted cover/Ballpit identity and a reference-led recommendation transition, but it must reveal real reading entry quickly and must not reinterpret ordinary wheel or touch scrolling as page turning. Expressive homepage motion never enters the article reader. Exact visual language remains an open redesign decision until reference comparison and repeated-use acceptance are complete.
