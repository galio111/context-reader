# Featured image scrolling: cover mitigation shipped, visual acceptance open

On 2026-09-23, the user supplied a screenshot of the homepage featured-article grid: four visible cards show large gray cover slots while one card has its image. The cover records are present. All 55 new articles had distinct first-party cover URLs and all 55 original cover URLs returned HTTP 200. The two published articles with no cover are older NPR rows from August, outside this run. A stored URL and HTTP success do not establish a timely visible paint.

The earlier implementation mounted most `<Image>` requests only within a 1200px band and sent them through `/_next/image`; a sampled first optimization request took about 4 seconds. Permanent `will-change: transform` on every image could also contribute to scroll stalls. Production `20260923T023100` switched to stored WebP directly, prepared the first 12 cards, started other requests 3600px ahead and removed permanent `will-change`. A fast-scrolling member could still overtake the download band across hundreds of cards.

Production `20260923T031100` adds a 96×72 WebP preview of the same stored cover to each published article's recommendation metadata. The server includes it in the compact catalogue; each card paints that embedded picture immediately, then reveals the full cover only after its load event. The pending card no longer shrinks while waiting. Publication and published-article edits regenerate the preview from the final first-party cover; automatic publication fails if a required cover preview cannot be generated. A reversible SQL backfill populated all 479 existing published covers while preserving `updated_at`; the two older text-only articles retain the designed text fallback. The catalogue increased from 609,120 to 1,419,592 UTF-8 bytes for 481 articles. This trades about 0.81 MB of catalogue transfer for no empty gray picture slot when scrolling outruns full-image loading.

The live API reports previews for 479/479 covers. The app browser's member-display preview, expanded to 431 cards, showed inline previews on 431/431 cards after a fresh reload; a deep-scroll screenshot showed actual pictures. This tests the member layout, but it does not use the owner's authenticated session or prove that every scroll speed feels seamless. The tiny preview can be softer than the full image. Acceptance still needs a cold-cache authenticated desktop and 390px mobile rapid-scroll check, particularly for frame stalls and visible sharpening; repeat separately in the Reader because body images use a different path. Keep the issue open until the user's visual acceptance.
