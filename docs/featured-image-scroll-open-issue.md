# Featured image scrolling: visual acceptance still open

On 2026-09-23, the user supplied a screenshot of the homepage featured-article grid: four visible cards show large gray cover slots while one card has its image. The cover records are present. All 55 new articles had distinct first-party cover URLs and all 55 original cover URLs returned HTTP 200. The two published articles with no cover are older NPR rows from August, outside this run. A stored URL and HTTP success do not establish a timely visible paint.

The production implementation mounted most `<Image>` requests only when a card entered a 1200px prefetch band, then sent them through `/_next/image`. A sampled cover optimization request took about 4 seconds on first use. The card CSS also reserved a compositor layer for every image via `will-change: transform`, which could contribute to scroll stalls. The pending change loads first-party WebP directly, preloads the first 12 visible-list cards after the opening, widens the prefetch band to 3600px, and removes permanent `will-change`. Direct cover assets are already bounded WebP and cache for a year.

Acceptance needs the live page with a cold cache, rapid downward and upward scrolling through many cards on desktop and 390px mobile. Inspect placeholder dwell, request timing, visible paint, scrolling long tasks, layout stability, and total bytes. Repeat in the Reader for article body images because the user also reported gray placeholders there earlier. A build or HTTP 200 is insufficient. Keep the issue open until live observation and the user's visual acceptance.
